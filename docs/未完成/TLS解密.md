# TLS 解密（方向 G）—— 设计，未开始

> **来源**：原 `docs/路线/开发方向和任务清单.md` §2 G（2026-10-21 拆出）。
> **状态**：⬜ 未开始｜**排期**：`docs/路线/开发路线图.md` 阶段 E（编号 31）
> **目标**：让加密流量**不再成为监测盲区** —— 解密后的明文进入同一条检测流水线，规则照常匹配。

---

## 0. 先明确三条事实（决定整个设计）

1. **密钥不在流量里。** TLS 的会话密钥由两端各自在进程内存中派生。抓包只能看到明文握手 + 密文。
   ⇒ 「读懂流量里用了什么密钥」这件事不存在。
2. **要拿到明文，只有三条路**：拿到密钥（SSLKEYLOGFILE）、钩住加密函数（eBPF）、做中间人（MITM）。
3. **本项目明确不做 MITM**（不重签证书、不改客户端配置）——这与"监测/取证"的定位一致。

---

## 1. 业界统一方案

主流开源产品（DeepFlow、Pixie、eCapture、Tetragon）的共同做法是
**eBPF uprobe 钩住 TLS 库的读写函数，直接取加密前的明文**——不需要密钥、不需要 MITM。

| 项目 | 机制 | 参考 |
|---|---|---|
| DeepFlow | `ssl_tracer.c` 钩 OpenSSL 系；`go_tls.bpf.c` 单独适配 Go | [ssl_tracer.c](https://github.com/deepflowio/deepflow/blob/c2c80912/agent/src/ebpf/user/ssl_tracer.c) |
| Pixie | 同一思路 | [Pixie eBPF 文档](https://docs.px.dev/about-pixie/pixie-ebpf/) |
| eCapture | 专门的 TLS 明文工具 | [eCapture](https://github.com/gojue/ecapture.cc/blob/master/src/en/1-introducing-ecapture/1.1-introduction-and-core-capabilities.md) |
| 业界共识 | 用户态 TLS tracing | [Tracing Summit 2023](https://tracingsummit.org/ts/2023/tls/) |

★ **共同的工程代价**：每个 TLS 库要**单独写钩子**，且要跟随版本（DeepFlow 就专门为
[OpenSSL 3.2.4+ 做过兼容修复](https://github.com/random-lambda/deepflow/commit/c90e67be0fc5525db1132671ded6aeda239ca004)）。
**这不是"配个开关"，是持续维护的适配工作。**

## 2. 四条技术路径对比

| 路径 | 原理 | 需要什么 | 覆盖率 | 本项目 |
|---|---|---|---|---|
| **A. eBPF uprobe** | 钩 `SSL_write/SSL_read` 等，拿**明文** | root + Linux 4.14+ | 高（多库适配后）| ✅ **主推** |
| **B. SSLKEYLOGFILE** | 应用主动导出 `CLIENT_RANDOM` 密钥 | 应用支持 + 配置 | 中（要应用配合）| ✅ 兜底 |
| **C. kTLS 钩子** | 钩内核 TLS 加解密函数 | kTLS 启用 | 中 | ✅ 补充 |
| D. 进程内存扫描 | 找 master_secret | root + 同机 | 低、脆弱 | ❌ **不做** |
| E. MITM 重签证书 | 中间人 | 客户端信任伪造 CA | 最高 | ❌ **不做** |

### 覆盖率现实（必须写进产品文档）

| 场景 | 能否解密 |
|---|---|
| OpenSSL / BoringSSL / GnuTLS / NSS / Go `crypto/tls`（同机 + root）| ✅ |
| kTLS（内核 TLS）| ✅ |
| QUIC / HTTP3（用户态实现）| ✅（钩 QUIC 库）|
| **自研 / 静态链接的 TLS 实现** | ❌ 找不到符号 |
| **网卡硬件卸载 TLS**（SmartNIC）| ❌ 明文在网卡 |
| **跨机部署**（抓包机 ≠ 业务机）| ❌ **数学上不可能** |

⇒ **目标 90~95%，不是 100%。**

## 3. ★ 最重要的一条：解不开的必须可见

> **监测盲区不是"解不开"，而是"解不开却不知道"。**

攻击者只需用一个自研 TLS 库就能绕过检测。如果产品静默漏掉，管理员会以为"没有攻击"。

**必须提供**：

- `crypto_unresolved_total` / `crypto_resolved_total` 两个计数器（按连接数）
- 会话详情里标注：`encrypted_unresolved`（能看到元数据，但内容不可读）
- 界面上一个常驻提示：**"本机有 N 个加密连接未能解密"**，可下钻看它们的目标 IP:端口
- 日志里出现未解密连接时**限流告警一次**（不要刷屏）

这条与"静默失效"是同一类问题（见技术债 #2 的教训）。

## 4. 分层设计

### L1 — 明文来源（本方向的核心工程）

| 优先级 | 手段 | 说明 |
|---|---|---|
| 1 | **eBPF uprobe** | 按库适配：OpenSSL / BoringSSL / GnuTLS / NSS / Go。每个库一套钩子 |
| 2 | **SSLKEYLOGFILE 监听** | 配置里给路径；应用支持时自动读取（兜底）|
| 3 | **kTLS** | 钩 `tls_encrypt/tls_decrypt` |

- 每个连接建立时，用 `client_random`（或 pid + fd + 栈信息）把"解密器"绑定到流上
- 明文按四元组 + 序号交回 L7 解析

### L2 — 解密与注入

- 解密发生在**归流之后、L7 解析之前**：HTTP/HTTP2 解析器完全不用改
- HTTP/2 需先解帧；HTTP/1.1 直接解析
- ★ **解密失败必须可观测**：返回"解密失败"状态，不要返回空 payload

### L3 — 合规与隐私

| 项 | 要求 |
|---|---|
| **明文默认不落盘** | 只保留元数据 + 命中证据片段（`snippet`，≤64 字节）|
| **明文留存上限** | 内存中 ≤ 24 小时；磁盘不存 |
| **日志脱敏** | 永不记录请求体、`Authorization`、`Cookie` |
| **解密动作审计** | 谁在何时开启解密、解了多少连接，写审计日志 |
| **启动确认** | 解密默认关闭；开启时打印"仅用于你拥有或已获书面授权的网络" |
| **导出** | 导出证据包时标注"含解密内容"，需二次确认 |

## 5. 明确不做

- ❌ **MITM / 重签证书 / 改客户端配置**（定位是"监测与取证"，不是"中间人代理"）
- ❌ **进程内存扫描密钥**（脆弱、易崩、跨版本失效）
- ❌ **云端密钥托管**（引入外部依赖与信任问题）
- ❌ 承诺"解密所有流量"（见 §2 覆盖率表）

## 6. 分阶段落地

| 阶段 | 内容 | 依赖 |
|---|---|---|
| G1 | SSLKEYLOGFILE 解析 + 归流绑定 + TLS1.2/1.3 record 解密（先手动给密钥打通链路）| 无 |
| G2 | eBPF uprobe 钩 **OpenSSL**（覆盖最广），自动拿明文 | Linux root |
| G3 | 扩展到 **Go / BoringSSL / GnuTLS / NSS** | 同上 |
| G4 | QUIC / kTLS 补充 | 同上 |
| G5 | 未解密连接的可观测性 + 合规审计（§3、§4-L3）| 无 |

★ **G1 必须先做**：没有它，无法验证"解密后的明文能否正确进入检测流水线"。
eBPF 只是"明文来源"，替换掉 G1 的手动输入即可。

## 7. 开源与法律边界

| 项 | 做法 |
|---|---|
| **许可证** | 倾向 **AGPLv3**（防止被拿去做闭源商业监控）；若选 Apache 2.0，需在 README 写清使用边界 |
| **使用条款** | 「**仅用于你拥有或已获书面授权的网络**」——README、启动日志、解密开启提示三处一致 |
| **免责声明** | 明确"误用与作者无关"，但**不假装能防止误用**（开源无法阻止） |
| **加密出口管制** | 部分国家对加密软件有出口限制，发行时需核查 |
| **不主动扫描** | 不扫描、不嗅探非本机/非授权网段的流量 |

## 8. 实现前必须回答的三个问题

1. **解密点放哪？** 归流后、L7 解析前（倾向此方案，HTTP 解析器零改动）。
2. **跨机怎么办？** eBPF 要求同机。跨机部署只能退回 SSLKEYLOGFILE，或明确告知"不可解密"。
3. **性能预算？** 每连接一次 uprobe 命中 + 一次 map 查找；明文复制有带宽成本，需压测与水位观测。
