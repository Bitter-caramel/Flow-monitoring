## 为什么必须有

现实流量里 HTTPS 占绝大多数。不解密，检测只能看到 SNI 与证书，**看不到请求体 / URI / UA**——而这恰恰是 Web 攻击特征所在。

**这是一项大工程**，但它决定"能不能真正看见攻击"，因此单独立方向，不塞进采集方向。

## G1 密钥来源（先做最实用的一种）

- `SSLKEYLOGFILE` 格式解析：`CLIENT_RANDOM <client_random> <master_secret>`
- 关联方式：TLS `ClientHello` 的 `client_random` → 该连接的会话密钥
- 其它来源（仅记录、先不做）：
  - RSA 私钥（只对 `TLS_RSA_*` 套件有效，现代已淘汰）
  - eBPF 钩明文（需 root，属采集方向变体）

## G2 TLS record 解密

- **TLS 1.2**：AES-GCM / AES-CBC + HMAC-SHA256(384)
- **TLS 1.3**：AES-GCM / CHACHA20-POLY1305；密钥由 HKDF 从 handshake secret 派生
- 解密后把明文交回 L7 解析（HTTP/2 需先解帧；HTTP/1.1 直接可解析）

## G3 归流期挂密钥

- 归流阶段识别 TLS 连接，把 `client_random` → 解密器 绑定到该流
- ★ **解密失败必须可观测**：不能像"静默失效"那样返回空

## G4 合规与边界（写进文档，不允许含糊）

- 只解密**有权抓取**的流量；部署前提与法律边界必须写清
- **不做主动 MITM**（不重签证书、不改客户端配置）——只做"被动抓包 + 密钥来源"，
  这与本项目"监测/取证"的定位一致

## G5 decrypted 标记要贯穿全链路

- 告警 / 证据里标注"该命中来自解密流量"，避免取证时把解密内容误当原始证据

## 实现前的三个前置问题（动手前必须先答）

1. **解密在哪里做？** 归流阶段（`reassembly` 之前）还是 L7 解析阶段（`decoder` 之后）？
   倾向：在归流后、L7 解析前，这样 HTTP 解析器完全不用改。
2. **密钥文件怎么给？** 环境变量路径 / 配置项 / 上传？抓包机与应用可能不在同一台。
3. **解密的性能预算？** 每流一次 AEAD 解密，量级与加解密硬件相关；要有丢包/水位观测。
