## 0. 一句话

> **检测引擎产出告警之后，本文负责三件事：**
> **① 把告警"送出去"（事件总线）；② 把告警"记下来"（sink，可查可关联）；③ 把流量"留下来"（全量 pcapng 留存 + 命中时切出证据）。**

★ **③ 是本文的重头**：**流量收集阶段就要把"全量留存"做好** ——
按**固定大小切成 pcapng 分段**、**按顺序命名**、可放**目录**也可**入库**、**被索引**、保留策略可配，
**为的是后续能随时"回放分析"**（拿留存的文件重放 → 复现当时看到的一切）。

## 1. 为什么"上总线"和"落库"两件都要做

这是被明确问过的问题，答案记在这里，免得后人再纠结：

> **总线 = 通知机制（当下广播给谁）；sink = 记忆机制（发生过什么、能查）。**
> **总线上没有历史；而且"当时的听众不在，这条告警就永久消失"。**

| # | 理由 |
|---|---|
| 1 | **时序不对称**：告警发生那一刻，想听的人可能还不存在（前端没打开、态势模块没上线、攻击链几小时后才来关联） |
| 2 | **安全分析的本质是回看**："昨天有哪些高危"、"这条规则最近命中过谁" —— 总线上查不到 |
| 3 | **关联/联合查询**：攻击链要判断"这几条告警是不是同一主机 + 同一时段 + 同一条流"，必须可按维度检索 |
| 4 | **进程重启即清空**：告警是**安全证据**，不能重启就没了 |
| 5 | **它本来就被定为"不可丢"**：事件线设计里 `alert.lifecycle` 属于「关键·不可丢」——**"不可丢"就意味着必须有持久落点** |

**一行告警 = 把"规则侧"和"流量侧"钉在一起的那颗钉子**：

```
一行告警 = (时间, 五元组, StreamID, 包定位, 规则ID, 命中缓冲, 偏移, 严重度)
              │        │        │         │
              │        │        │         └─→ 定位到**具体那个包**（10-1 新增，之前缺）
              │        │        └───────────→ 该流的原始包 / 流统计
              │        └────────────────────→ 同时段其它告警 → 攻击链关联
              └─────────────────────────────→ 规则详情（类别 / 严重度）
```

## 2. `detect.Alert` 的完整字段（10-1 要补包定位）

现状（`internal/modules/detect/engine.go`）：`RuleID / Name / Severity / Weight / Time /
SrcIP / SrcPort / DstIP / DstPort / Proto / StreamID / Buffer / Offset / Snippet`。

**要补的字段**：

| 字段 | 说明 |
|---|---|
| `PktNo int` | **包序号**（来自 `Packet.No`，从 1 开始）★ 这是"从告警跳回那个包"的关键，之前没有它，这条链是断的 |
| `FlowKey string` | 规范化五元组的可读形式（如 `"10.0.0.5:50000->93.184.216.34:80/tcp"`）——**给人和数据库查询用**，避免每次现拼 |

> **不加** `CaptureID`：因为"这是哪一次抓包 / 哪一次导入"是**流水线运行**的属性，不是告警本身的属性 ——
> 它放在事件信封里（见 §3），由调用方填。

## 3. 事件线：`alert.lifecycle`

```go
// internal/modules/alert
const TopicAlertLifecycle = "alert.lifecycle"

// Event 是发布到 alert.lifecycle 的事件。
// CaptureID 由**调用方**填（命令行回放填文件名、导入填导入批次号）。
type Event struct {
    CaptureID string       `json:"capture_id"`
    Alert     detect.Alert `json:"alert"`
}
```

- **P0 一条告警一个事件**（简单、好排查）；**P1 再考虑成批**（高流量下事件数量大）。
- 订阅缓冲：`bus.Subscribe(TopicAlertLifecycle, 4096)`；★ 因为该线是「不可丢」类，
  **必须把 `bus.Dropped()` 当指标盯着**（丢弃 = 证据缺失，要告警）。
- 负载必须是**可 JSON 序列化**的（将来消费者搬进独立插件进程时直接复用，不用改形状）。

## 4. sink 接口与两种实现

```go
// Sink 是告警的落点。
type Sink interface {
    Write(ev Event) error   // 写一条（实现内部可缓冲）
    Flush() error           // 冲刷缓冲（退出前必须调用）
    Close() error
}
```

| 实现 | 用在哪 | 为什么 |
|---|---|---|
| **`FileSink`** | `parse-cli`（单机回放 / 命令行） | **不依赖数据库**，开箱即用；格式为 **JSON Lines**（一行一条，便于 `grep`/`jq`/追加） |
| **`PGSink`** | 服务端 / importer 那条路 | 能按维度检索、能关联（正是 §1 第 3 条要的） |

> 两者用**同一个接口**：命令行也允许选择写 PG（给了连接串就用 PG）。

### 4.1 PG 表结构（追加到 `internal/modules/store/schema.sql`）

```sql
CREATE TABLE IF NOT EXISTS alerts (
    id          BIGSERIAL PRIMARY KEY,
    ts          TIMESTAMPTZ NOT NULL,          -- 命中时刻（包时间）
    capture_id  TEXT        NOT NULL,          -- 哪一次抓包 / 导入
    rule_id     TEXT        NOT NULL,
    rule_name   TEXT,
    severity    TEXT,
    weight      INT,
    src_ip      TEXT, src_port INT,
    dst_ip      TEXT, dst_port INT,
    proto       TEXT,
    flow_key    TEXT,                          -- 可读五元组
    stream_id   BIGINT,                        -- 流 ID（-1 = 未归属）
    pkt_no      BIGINT,                        -- ★ 包序号
    buffer      TEXT,                          -- 命中在哪个缓冲区
    hit_offset  INT,
    snippet     TEXT,
    hits        INT DEFAULT 1,                 -- 去重窗口内累计次数（见 §7）
    evidence    TEXT,                          -- 证据文件路径（见 §5），无则 NULL
    created_at  TIMESTAMPTZ DEFAULT now()
);

-- ★ 这些索引就是"给未来的告警查询和联合查询用的"
CREATE INDEX IF NOT EXISTS idx_alerts_ts        ON alerts (ts DESC);
CREATE INDEX IF NOT EXISTS idx_alerts_rule_ts   ON alerts (rule_id, ts DESC);
CREATE INDEX IF NOT EXISTS idx_alerts_src_ts    ON alerts (src_ip, ts DESC);
CREATE INDEX IF NOT EXISTS idx_alerts_dst_ts    ON alerts (dst_ip, ts DESC);
CREATE INDEX IF NOT EXISTS idx_alerts_stream    ON alerts (stream_id);
CREATE INDEX IF NOT EXISTS idx_alerts_capture   ON alerts (capture_id);
```

### 4.2 JSONL 格式

一行一个 `Event` 的 JSON（字段名与 §3/§2 一致），**追加写**、每写一条 `Flush`。
不要写数组包装（方便边跑边看、方便 `tail -f`）。

### 4.3 留存段的索引（★ "被索引"落在这里）

每写完一段就在索引里登记一行；**目录模式**同时写一份 `index.jsonl`（脱离数据库也能查 ✓）；
**入库模式**写下面这张表（表名**管理员自定义**，默认 `capture_segments`）：

```sql
CREATE TABLE IF NOT EXISTS capture_segments (
    id           BIGSERIAL PRIMARY KEY,
    capture_id   TEXT        NOT NULL,
    seg_no       BIGINT      NOT NULL,          -- 段序号（单调递增，体现顺序）
    name         TEXT,                          -- 目录模式：文件名；入库模式：NULL
    seg_bytes    BIGINT      NOT NULL,          -- 本段字节数（定长，最后一段可能小）
    packet_cnt   BIGINT      NOT NULL,
    start_ts     TIMESTAMPTZ NOT NULL,
    end_ts       TIMESTAMPTZ NOT NULL,
    storage      TEXT        NOT NULL,          -- 'file' / 'db'
    blob         BYTEA,                         -- 入库模式：整段 pcapng 字节
    deleted      BOOLEAN DEFAULT FALSE,         -- 已被保留策略删除
    created_at   TIMESTAMPTZ DEFAULT now(),
    UNIQUE (capture_id, seg_no)
);

CREATE INDEX IF NOT EXISTS idx_seg_capture_time ON capture_segments (capture_id, start_ts DESC);
CREATE INDEX IF NOT EXISTS idx_seg_time         ON capture_segments (start_ts DESC);
```

**按时间找段**（证据提取时用）就是一句：
`WHERE capture_id = ? AND start_ts <= t2 AND end_ts >= t1 ORDER BY seg_no` ✓。

## 5. 流量留存与证据提取（★ 本文重头）

分两层，**职责不同，别混**：

| 层 | 做什么 | 生命周期 |
|---|---|---|
| **① 全量留存** | **所有**流量持续写成 pcapng，**按固定大小切成段**，顺序命名，被索引 | 长期；按保留策略**轮转覆盖**旧的 |
| **② 证据提取** | 命中告警时，从留存里**切出 `[t-窗口, t+窗口]`**，**独立另存**一份 pcapng | 永久（**不随轮转被删**，因为它已经独立出来了） |

★ **为什么证据要"独立另存"而不是"记个偏移量"**：留存段会被**轮转覆盖** ✗ ——
证据必须**脱离轮转生命周期**，才能拿去归档、给别人、以后复查 ✓。

### 5.1 全量留存：定长轮转段

- **写什么**：每一个包（**未解码的原始帧** —— 保留最原始的事实，解码随时可重做）；
- **怎么切**：**大体定长**（默认 64 MB）。写到 **≥ 该值就封段**、开下一段；
  ★ **绝不拆包**（一个包必须完整落在一段里），所以段大小会有小幅波动 —— **"差不多就行"** ✓；
- **怎么命名**：**名字体现顺序** —— `<capture-id>-<6 位序号>-<段起始时间>.pcapng`
  （如 `run-000001-20261012T201530.pcapng`），序号单调递增、零填充便于排序 ✓；
  ★ 这个命名**对齐 dumpcap 环形缓冲的做法**（它的文件名是 `outfile_00001_20260714120117.pcapng`：序号 + 创建时间）；
- **放哪里**（★ **管理员自定义**，二选一）：
  - **目录**（默认）：`<RootDir>/<capture-id>/`，每段一个文件 ✓；
  - **入库**：每段一行（`BYTEA`），放进**管理员自定义的表名** ✓；
- **索引**：每封一段就登记一行 —— 段号 / 文件名或主键 / 起止时间 / 包数 / 字节数 ✓（见 §4.3）；
- **保留策略**（★ 管理员可配）：按 **最大段数** / **最大总字节** / **最长保留小时** 三选一，
  超了就从**最老的段**开始删（删段时同步标索引行 `deleted = TRUE`）✓。

> ★ **`parse-cli` 回放路径的差异**：它读进来的那个文件**本身就是"全量留存"** ✓ ——
> 所以 CLI 上**不需要再写一份留存**（那是复制，没意义），只需要 ② **切证据**（从输入文件里切）✓。
> 全量留存真正发挥作用的地方是**实时监听（P1）**与 importer 那条路 ✓ ——
> **但机制现在就建好**，这样"收集阶段"一开工就是对的，不用返工 ✓。

### 5.2 两条存储路径：**内存环形缓冲（快）+ 磁盘留存（慢）**

**★ 它们不是二选一，而是互补** —— 这是本设计的关键：

| 路径 | 介质 | 干什么 | 特点 |
|---|---|---|---|
| **① 内存环形缓冲** | 内存 | **供"取证据"** | 零回读；★ **不受轮转删除影响**（数据一定在）✓ |
| **② 全量定长留存** | 磁盘 | **供"回放"**，并给取证据**兜底** | 顺序追加写（便宜）；覆盖全时段 ✓ |

**为什么两条都要**：

- **只有磁盘** ⇒ 取证据要**随机回读**（贵，而且和顺序写抢 IO ✗），
  而且**轮转可能已经把那段删了** ⇒ 证据直接没了 ✗；
- **只有内存** ⇒ 装不下全时段 ✗，也**没法回放** ✗；
- **两条都有** ⇒ 常见情况下证据从内存直接拿（**磁盘访问模式保持纯顺序** ✓），
  内存里没有的部分再回读留存段补齐 ✓。

> ★ 当初"取消环形缓冲"的想法是错的：它只看了"数据在不在磁盘上"，
> **漏算了回读的代价**和**轮转删除**这两件事。

> ★★ **2026-10-12 追加（重要）：环形缓冲是"缓存"，不是"账本"。**
>
> 起因：并发生产者会让**包时间乱序**（正常现象）。那么"顺序正确"该在哪一层解决？结论是分三层：
>
> | 环节 | 按什么顺序 | 代价 | 说明 |
> |---|---|---|---|
> | **写入**（入环 / 落盘） | **到达顺序**（append） | 零 | ★ 必须保持便宜；业界 `dumpcap` 环形缓冲也这样 —— **写时不管时间序**，由 Wireshark 在读时按时间戳展示 / 重排 |
> | **读取**（`Slice` / 切证据） | **时间顺序** | 只对取出的几十~几百帧排序 | ★ 在**冷路径**做，几乎免费 |
> | **淘汰** | **近似**（按到达顺序从最老端丢） | 零 | 正确性**不靠它**（见下） |
>
> - **`Slice` 必须全扫**（不能假定"后面一定更晚"），且**返回前按时间排序** ✓；
> - **淘汰近似是可接受的**：可能多留几帧旧的、极端情况下甚至先丢到较新的帧 ✗ ——
>   但 ★ **内存由 `MaxBytes` 严格兜底**（不会无界增长 ✓），
>   而 ★★ **证据完整性由磁盘留存负责** ✓（它不是缓存，在保留策略内不淘汰、可随意扫描）；
> - ★ **不做**"写入时维持时间有序"：有序切片要**每包 memmove 十万个帧头（≈2MB/包）** ✗✗ 热路径不可接受；
>   最小堆虽只 O(log n)，但**收益极小**（丢掉的磁盘上还有）✓。
>
> ★★ **由此推出一条给 10-4 的红线**：
> **证据提取必须"真的去兜底"** —— 从环里拿到的只是**一部分**，
> **缺口必须回读留存段补齐** ✗（**绝不能"环里没有就算了"** ✗），
> 并把"**哪段来自内存、哪段来自磁盘**"写进边车 ✓。

### 5.3 证据提取（内存优先、磁盘兜底）

- **触发**：告警到达时；
- **范围**：`[告警时刻 - WindowMs, 告警时刻 + WindowMs]`（默认前后各 5 秒）；
  ★ **P0 按时间窗切，不按流切**（跨流的关联攻击也要能一起留证）；
- **★ 需要一个"待收集窗口"**：告警发生的那一刻，`t + 窗口` 的包**还没来** ✗ ——
  所以要开一个待收集窗口，等时间走到 `t + WindowMs` 再落盘；
- **取数据（★ 三级回退，每一级都要在边车里记清楚用了哪级）**：
  1. **内存环形缓冲**里有 → 直接拿（**常见路径，零回读** ✓）；
     ★ 但环是**缓存**、淘汰是**近似**的 → **它可能缺帧** ✗ →
     **必须**用第 2 级把缺口补上，**不能"环里没有就算了"** ✗；
  2. 缺的部分 → **回读留存段**补齐 ✓；
  3. 两边都没有 → **仍然产出证据文件**，边车标 `incomplete: true` + 写清原因 ✓（绝不静默少给 ✗）；
- **合并**：**同一时间窗内的多条告警合并成一个证据文件**（否则一次攻击会生成几十个文件 ✗）；
- **输出**：`<EvidenceDir>/<capture-id>/<起始时间>-<首个规则ID>.pcapng`
  \+ 一份同名 `.json` **边车**（覆盖了哪些告警、时间范围、包数、**数据来自哪几级**）—— **证据自描述** ✓。

> ★ **告警风暴是这里唯一的性能风险**（每秒几千条告警 → 反复回读同一个窗口 ✗）——
> 所以 **§7 的最小去重同时也是性能保护** ✓（同规则 + 同流只切一次）。

### 5.4 参数与默认值（★ 全部管理员可自定义）

| 参数 | 默认 | 说明 |
|---|---|---|
| `RingBytes` | **64 MB** | ★ **内存环形缓冲上限**；超了从最老的丢（丢掉的靠磁盘留存兜底） |
| `SegmentBytes` | **64 MB** | 全量留存的**段大小**（★ **松要求**：写到 ≥ 该值就封段、绝不拆包，大小会小幅波动） |
| `RetentionSegments` | **100** | 保留多少段（≈ 6.4 GB）；也可改用下面两个 |
| `RetentionBytes` / `RetentionHours` | 0（不启用） | 与上面**三选一**；同时给了就取最严格的 |
| `RootDir` | `capture/` | 留存根目录（目录模式） |
| `Storage` | `file` | `file` / `db`（入库：每段一行 `BYTEA`） |
| `StoreTable` | `capture_segments` | 入库时的**表名**（★ 管理员自定义） |
| `WindowMs` | **5000** | 证据窗口：命中时刻前后各 5 秒 |
| `EvidenceDir` | `evidence/` | 证据根目录 |
| `MaxEvidenceBytes` | **256 MB** | 单个证据文件上限（超了截断并在边车里标注） |
| `DedupWindowMs` | **10000** | 告警去重窗口（见 §7） |

**覆盖方式**：代码里写死默认值 → ① 配置文件（`internal/kernel/config` 的 YAML 底座）；
② `parse-cli` 命令行开关（`--collect-*`）覆盖 ✓。

### 5.5 程序流程（★ 顺序与位置都不能错）

```
收包
 └→ 解码（L2~L7）
      ├─① 内存环形缓冲（RingBytes 上限）           ← 快路：供取证据，零回读
      ├─② 全量留存（定长轮转段，顺序追加 + 段索引）← 慢路：供回放，并兜底
      └─③ 归流 → 检测 → 命中
                        │
                        └─→ 开"待收集窗口"（等到 t+W；窗口内的包继续并入）
                                  │
                                  └─→ 取证据：内存优先 → 磁盘兜底 → 都缺则标 incomplete
                                  │
                                  └─→ 写【独立证据 pcapng】+ 边车 JSON
```

★ **两条红线**：

1. **顺序**：**留存 / 喂缓冲 必须在检测之前** —— 否则"命中那一刻之前的包"两头都没有 ✗；
2. ★ **不能存切片**：环形缓冲里存的是**原始帧**，实现上**必须复制、绝不能存 `p.Data` 的切片** ✗ ——
   回放 / 文件路径下缓冲区虽然稳定，但**实时抓包的缓冲区会被复用** ✗
   （本项目踩过一次的生命周期坑）。★★ **2026-10-12 更正**：本文原写"P0 的实现是切片，P1 再换成复制" ——
   那等于**埋了一个静默出错的地雷**（哪天接上实时抓包，就会悄悄读到脏数据）。
   **现改为：P0 直接复制（正确优先、实现简单）**；P1 若复制真成瓶颈，再评估"借用 + 证明缓冲区稳定"，
   且必须用测试锁住该前提 ✓。

### 5.6 P0 / P1 的能力边界（★ 别承诺做不到的事）

| 能力 | P0 | P1 |
|---|---|---|
| 证据范围 | **时间窗**（前后各 5 秒） | ★ **整条连接**（按流 / 按连接导出） |
| 怎么做到 | 环形缓冲按**时间**组织 | 环形缓冲升级为**按流缓存**（每流一个缓冲 + 老化 + memcap）—— **这正是 TCP 重组要用的那套流缓冲**，届时天然就有 ✓ |

> **P0 不假装能给出"整条连接"**：一条持续 30 秒的连接，10 秒窗口只能截到一段 ✓（如实记录在边车里）。

## 6. pcapng 写入器（一套代码，两种用法）

**决定：写一个最小的 pcapng 写入器，而不是自创格式。**
理由：安全分析里"证据能直接丢进 Wireshark 打开"是刚需；**留存文件还要能回放**；
而且这与本项目"**不发明格式，复用事实标准**"的既定红线一致（和当初选 Suricata 规则格式同一个道理）。

同一个写入器支撑两种用法：

| 用法 | 谁用 | 特点 |
|---|---|---|
| **段写入器**（轮转） | ① 全量留存 | 写到 `SegmentBytes` 就**封段**，由上层开下一段；文件名由上层给 |
| **证据写入器**（单文件） | ② 证据提取 | 从留存段里**读出**覆盖窗口的帧，写成一个**独立完整**的 pcapng + 边车 JSON |

- 范围：**Section Header Block + Interface Description Block + Enhanced Packet Block** 三种块够用；
- **时间戳要保真**（写 pcapng 的高精度时间戳选项；至少微秒级，与读入时的 `tsresol` 对齐）；
- 读出侧我们**已经有 pcapng reader** ✓ → 可做"**写出去再读回来**"的**往返测试** ✓；
- ★ **P0 要写的唯一选项**：SHB 的 **`shb_userappl`**（选项码 3）= `"flow-monitoring"`
  —— 也就是"这个文件是谁生成的" ✓；而且**我们自己的 reader 已经能解析它** ✓
  → 往返测试顺带覆盖"选项解析"这条路 ✓；
- 不做：压缩块、其它自定义选项、多接口（P0 单接口）。

### 6.1 业界对照（照抄成熟做法，不发明轮子）

| 我们做的事 | 业界对应 | 出处 |
|---|---|---|
| **全量留存**：定长段 + 保留 N 段 + 满了覆盖最老的 | dumpcap 的**环形缓冲** `-b filesize:1000 -b files:5`（手册原话："form a ring buffer"） | [dumpcap(1)](https://www.wireshark.org/docs/man-pages/dumpcap.html) |
| **命中时切出独立证据** | Wireshark 的 **"Export Specified Packets"**（把选中的包导出成**新** pcapng）—— ★ 我们是**自动**按告警时间窗做 | Wireshark 菜单 |
| **段命名带序号与时间** | dumpcap 的 `outfile_00001_20260714120117.pcapng` | 同上 |
| ★ **证据不是"文件切割"** | 一个段里可能既有窗口内也有窗口外的包、窗口还可能横跨两段 → 必须**挑出窗口内的包重新封装**成完整 pcapng（= Export Specified Packets 的语义） | — |

## 7. 最小去重

同一 `(rule_id, stream_id)` 在**去重窗口**（默认 **10 秒**）内只落一条告警，
后续命中**累加 `hits`** 计数（不新增行）。

- 为什么 P0 就要有：否则一条规则命中了同一流的 2000 个包，就会写 2000 条告警 —— 报告和库都会被淹没；
- 去重放在 **sink 之前**（消费者侧），**不影响检测引擎**（引擎永远老老实实报每一次命中）。

## 8. P0 明确不做

| 不做 | 何时做 |
|---|---|
| 告警的确认 / 关闭 / 处置状态机（ACK、工单） | P1（处置模块） |
| 态势评分、攻击链关联算法 | P1（态势 / 攻击链模块） |
| 告警外发（syslog / webhook / 邮件） | P1 |
| **实时监听（网卡抓包）本身** | P1 —— **但"全量留存 + 索引 + 轮转"机制现在就建好**（收集阶段一开工就是对的） |
| **"整条连接"级证据**（按流导出） | P1 —— 与 **TCP 重组**一起做（那时才有按流 / 按连接的流缓冲，见 §5.6） |
| 证据的归档压缩 / 冷热分层 / 远程对象存储 | P1（P0 只做本地目录或入库） |
| 成批事件、事件压缩 | P1 |
| 前端页面 | 数据面稳定后再做（既定：前端按需引入） |

## 9. 测试策略

1. **内存环形缓冲**：`RingBytes` 上限生效、淘汰顺序正确（最老的先丢）、
   窗口内的包能完整取出；★ **未淘汰的数据不得回读磁盘**（用计数器断言"回读次数 == 0"）；
2. **留存段写入器**：写到 ≥ `SegmentBytes` 会**封段并开新段**；**命名顺序正确、零填充**；
   **绝不拆包**（每个包完整落在某一段里）；索引行（段号 / 起止时间 / 包数 / 字节数）正确；
3. **保留策略**：超 `RetentionSegments` / `RetentionBytes` / `RetentionHours` 时，
   **从最老的段开始删**且索引行被标 `deleted`；
4. **证据提取**：时间窗切得准（边界包不多不少）；同窗多条告警**合并成一个文件**；
   **内存优先**（内存里有时不得回读）；内存缺、磁盘补时边车要标出数据来源；
   ★ **两边都缺时要产出文件并标 `incomplete`**（绝不能静默少给）；
5. **pcapng 写入器往返**：写出去的段 / 证据用**我们自己的 reader** 读回来，**逐包比对字节与时间戳**；
6. **sink**：`FileSink` JSONL 往返；`PGSink` 的集成测试需要 PG 实例（**没有就 `t.Skip`**，别让 CI 依赖数据库）；
7. **去重**：同 `(rule,stream)` 在窗口内只出一条、`hits` 累加正确；跨窗口要分两条；
8. **端到端**：样本 + 规则 → `parse-cli --detect --collect` → 断言
   ① JSONL 里的告警字段正确 ② 证据文件存在且**能被读回** ③ 证据里**确实包含命中那个包**；
9. ★ 每条新回归网都要**用"故意破坏"证明它会红一次**（踩坑 15 的配套动作）。

## 10. 与其它模块的关系

```
检测引擎(detect) ──命中──▶ 事件总线 alert.lifecycle ──▶ 告警消费者(alert 模块)
                                  │                        │
                                  │                        ├─▶ 最小去重
                                  │                        └─▶ Sink：FileSink(JSONL) / PGSink
                                  │
                                  └──（同一条总线上的其它线：detect.feature / situation.level /
                                       disposal.audit / attackchain.evidence / capture.health）

流量留存(collect) 在**热路径**上、且必须在**检测之前**被喂到：
  ① 全量留存：每包 → 定长轮转段(pcapng) + 段索引
  ② 证据提取：告警 → 待收集窗口 → 从段里切出独立 pcapng + 边车 JSON
```

★ **依赖方向**：`alert` / `collect` → `detect`（只为 `Alert` 类型）、`eventbus`、`datamodel`、`pcapng`；
**`detect` 不认识它们**（引擎只管产出告警，不管谁消费、也不管谁留存）。
