# 测试规范与指南（给开发者 / 给 agent）

> **这份文档管什么**：怎么写测试、什么症状用什么手法、哪些坑特别隐蔽、联动测试怎么设计、给 agent 下测试指令时的规范。
> **管不到什么**：具体某个模块的用例清单（那些跟着任务记录走）、测试环境搭建（见 `docs/项目状态.md` §七）。
> **一句话立场**：**测试不是"证明代码能跑"，是"证明它在该错的时候会红"。**

---

## 1. 本项目的测试形状：不是金字塔，是菱形

业界主流是 [测试金字塔](http://www.cs.cmu.edu/~aldrich/courses/15-413/slides/04-testing.pdf)（单元多 / 集成中 / e2e 少），
前端圈流行 [Testing Trophy](https://stevekinney.com/courses/enterprise-ui/testing-at-scale)（集成比重更高）。
两者都成立，但**它们假设 bug 主要来自"逻辑算错"**。

本项目不是。我们历史上抓到的严重缺陷，绝大多数是：

- **链路接错**（数据没从 A 流到 B）—— 单元测试看不见
- **静默失效**（索引查不到、缓冲取错、网络族不支持 ⇒ 结果为空但"不报错"）
- **维度缺失**（只测 IPv4、只测单包、只测非加密）
- **声明与实现漂移**（清单说它是进程，实际是库）

⇒ 所以本项目的形状是**菱形**：底部保留大量单元测试，**中间那层（集成/e2e）特别厚**。
判据：**"这条测试能不能发现'不报错但结果不对'？"** 不能的话，它只值很少。

## 2. 写测试的十条硬规范

1. **一个测试只断言一个行为**，名字说清断什么。
   推荐：`TestXxx_WhenY_ShouldZ`；中文说明写"为什么必须有这条"。
2. **断言必须可证伪**：给出**具体数字 / 集合 / 字节**。
   禁止 `!= nil`、`> 0`、`>= 1` 这类"存在性断言"（见 §3）。
3. **集合用相等，不用包含**。命中集合要 `reflect.DeepEqual(got, want)`，
   而不是 `strings.Contains`（后者会把"多命中一条"也判成绿）。
4. **夹具用 `t.TempDir()`**，不依赖仓库里的真实文件；
   唯一例外是"真实清单守卫"类测试（它故意要校验仓库里的 json）。
5. **不 mock 真实环境**。DB / 文件系统 / 子进程 / 网络，**必须至少真跑一次**；
   替身只用来补语义与边界，不能替代真实验证（坑 29：只用内存替身跑真 SQL ⇒ 等于没验）。
6. **字节敏感产物要防行尾**：逐字节比对的夹具先归一化 `\r\n`，并给目录加 `eol=lf`（坑 13）。
7. **输出必须可复现**：map 渲染前排序、不写时间戳、不依赖文件系统遍历顺序。
   判据：连跑两次结果完全一致。
8. **测试要能单独跑通**：`go test -run '^TestX$'` 必须独立成功（不许依赖其它测试的副作用）。
9. **新功能必须带"不该命中"的用例**（误报基线）。只有正例的测试是半个测试。
10. **每条新增的守卫型断言，必须做一次变异验证**（见 §3）。没红过的断言不可信。

## 3. 断言强度与变异测试（本节最值钱）

### 3.1 弱断言为什么害人

真实案例（坑 24）：一条号称"顺序写反就会红"的测试，断言是 `命中次数 > 0`。
故意把顺序换掉后，命中从 13 掉到 6 —— **仍然 > 0，测试照样绿**。

⇒ **弱断言守不住任何东西**，它给人的安全感是假的。

### 3.2 变异测试怎么做（本项目约定）

1. **首选仓库外副本**：`D:\tmp\mut-<任务>\` 复制 → 改坏 → 跑 → 丢弃，风险为零。
2. 在仓库内做时：**先备份 + 事后校验哈希 + 在报告里说明**。
3. **改法要指向"这条断言想守的那个点"**，而不是随便改坏一行。
   例：验证 sid 越界拦截 ⇒ 把 `continue` 去掉，看"越界规则是否混进结果"。
4. **看红在哪**：报错信息必须精确（`Programs 条数 = 2, want 1`），
   而不是"测试失败"——后者说明断言太粗。

### 3.3 判据

> **"我把这处改坏，它会红在正确的位置吗？"** 会 ⇒ 断言有效；不会 ⇒ 重写。

参考：[muttest（R 包，变异测试的入门读物）](https://cloud.r-project.org/web/packages/muttest/readme/README.html)。

## 4. 黑盒手法：按"要证明什么"选方法

| 要证明什么 | 手法 | 本项目实例 |
|---|---|---|
| 输入域被正确划分 | **等价类划分** | 规则来源：builtin/custom/suricata/public/未知 |
| 边界不越界 | **边界值分析** | sid 号段边界 `999_999` / `1_000_000` 两侧各测一次 |
| 多条件组合不错 | **决策表** | `InProcess × Core × HasBinary` 三态判定顺序 |
| 生命周期状态正确 | **状态迁移** | 模块 `launched → started → stopped → error`；启停幂等 |
| 端到端业务通 | **场景法** | `pcapng → 解码 → 归流 → 检测 → 告警` |
| 异常输入不崩 | **错误猜测** | 空清单、缺 sid、非法 sid、目录不存在、重复 sid |
| 性能不退化 | **基线对比** | 热路径零分配；规则集加载耗时 |

> 通用手法参考：[软件测试方法与过程（51Testing）](http://www.51testing.com/mobile/view.php?itemid=219358)、
> [CMU 15-413 Testing 讲义](http://www.cs.cmu.edu/~aldrich/courses/15-413/slides/04-testing.pdf)。

## 5. 白盒检查：按"症状"定位（实战版）

这一节是本项目自己的经验积累，**症状 → 先查什么**：

| 症状 | 先查什么 | 我们踩过的 |
|---|---|---|
| **测试全绿但功能明显不对** | 被测代码的**每个分支**是否都有用例走到；索引/映射类要分别测"查得到"和"查不到" | 坑 15：协议索引用展示名当键 ⇒ 所有限定协议的规则被静默跳过，11 个测试全绿 |
| **命中数"看起来对"但行为可疑** | 命中落在**哪个缓冲/哪条分支**；去重键是否塌陷 | 坑 22/23：粘性缓冲写反、`StreamID=-1` 导致告警去重塌陷 |
| **某个维度整体失效** | 数据维度覆盖：IPv4/IPv6、单包/跨包、明文/加密 | 坑 23：analyzer 只归并 IPv4 ⇒ IPv6 的 `stream` 缓冲变哑巴 |
| **偏移/长度算错** | 是不是"从帧尾反算"；帧尾填充与截断 | 坑 26：以太网最小帧填充 ⇒ `payloadOffset` 偏 2 字节 |
| **改了默认值/语义，测试没红** | 是否跑了**全量**与 golden；影响面是 grep 反推的 | 坑 25：grep 漏掉用 `LoadFile` 的 e2e 测试 |
| **真实环境一跑就出问题** | 是否只用了内存替身 | 坑 29：真 SQL 一次没在真库执行过 |
| **"没搜到"就当"没有"** | 命令本身是否被截断（`--limit`、`Select-Object -First N`、管道） | 坑 42：一天内踩三次，把"18 个包"说成"3 个包" |
| **测试构造错了却像实现坏了** | 先打印实现的实际输出，再判断 | 坑 49：14-1 里在 public 段放 `sid:2000003` 想测"重复"，结果先被"越界"拦下 |
| **文档说一套、代码做一套** | 拿代码撞文档（红线 7） | 坑 48：只核实一个字段，结果 5 份文档 5 份都有错 |

## 6. 联动测试：单模块绿 ≠ 链路通

### 6.1 什么时候必须写联动测试

只要一个功能**跨了两个及以上模块/进程/存储**，就必须有一条端到端测试：
`rule → detect`、`detect → alert`、`capture → hotpath → detect`、`modulecontrol → fs` …

### 6.2 三个必备断言（缺一个就不算联动测试）

1. **输出集合相等**（不是"至少一条"）：每个输入对应的命中/结果要精确。
2. **误报基线为零**：正常输入必须一条不报（`testdata/attacks/normal.pcapng` 就是这个用途）。
3. **计数自洽**：报告里的条数 = 实际结果条数（防"报告说命中但结果为空"）。

### 6.3 通过改代码限定测试范围（用户明确要求的方式）

联动测试容易"一跑一大片、失败不知道错在哪"。做法：
- 临时**收窄输入**（只跑一个样本 / 只开一条规则）
- 临时**注入观测点**（打印中间集合大小）
- 临时**跳过无关断言**（用 `t.Skip` 但**必须事后恢复**）
- 这些临时改动**必须在报告里说明**，并确认 `git status` 干净

> 现状样板：`cmd/parse-cli/e2e_rules_dir_test.go` —— 6 个样本 × 精确命中集合，
> 其中 `normal` 断言"零命中"，`traversal` 断言"自写与社区规则各命中一次"。

### 6.4 真实环境

- PG：`$env:FLOW_TEST_PG_DSN="postgres://flow:flow@127.0.0.1:5433/flow?sslmode=disable"`
  （不设则 skip；设了必须真连）
- 真进程：`$env:FLOW_TEST_PLUGIN=1`（真启停插件进程，含超时强杀）
- **判据**：这段 SQL / IO / 进程操作，**有没有在真实环境里被真正执行过？** 答不上来就是没验完。

## 7. 测试坑专章（隐蔽、耗时、值钱）

> 这一章单独开，是因为这些坑**人工查和 agent 查都要花很久**，直接写出来最省命。

| # | 坑 | 现象 | 为什么隐蔽 | 怎么早发现 |
|---|---|---|---|---|
| 坑 13 | golden 先绿后红 | agent 刚写完测试是绿的，提交/检出后红 | `.gitattributes` 的 `text=auto` 让检出变 CRLF | 字节比对前归一化 + 夹具目录锁 `eol=lf` |
| 坑 15 | 索引用展示名当键 | 所有限定协议的规则被静默跳过 | 用例全是 `ProtoAny`，索引那条路一次没走 | 按**代码分支**列测试清单，"查得到/查不到"各测一次 |
| 坑 22 | 粘性缓冲位置写反 | 匹配结果莫名退回 `payload` | 命中数仍然正常 | 断言"命中落在哪个 `Buffer`" |
| 坑 23 | IPv6 整体变哑巴 | `stream` 缓冲在 IPv6 上恒空 | 夹具全是 IPv4 | 每个维度至少一个反例样本 |
| 坑 24 | 弱断言 | 故意破坏后测试照样绿 | 它"通过"了 | 每条新断言做变异验证 |
| 坑 25 | 影响面靠 grep 反推 | 改了默认值，漏掉用 `LoadFile` 的测试 | grep 不到间接调用 | 副本里跑全量，用**红名单**反推 |
| 坑 26 | 帧尾反算偏移 | 载荷偏移偏 2 字节 | 合成夹具恰好没填充（巧合正确） | 夹具必须含"带尾部填充的帧" |
| 坑 29 | 只用替身验证 | 真 SQL 从未在真库执行 | 单测全绿 | 集成测试开关 + 真实环境跑一次 |
| 坑 36 | agent"实现做完、测试为零" | 交付物达标但没有测试文件 | 报告里可能还写着 Success | **范围本身就是根因**：把"写测试"单独派一轮 |
| 坑 42 | 输出被截断 | "没搜到"当成"没有" | 命令没报错 | 先收进变量再筛；关键词搜索别配 `-First N` |
| 坑 46 | 哨兵错误没映射状态码 | 语义拒绝返回 500 | 服务层测试是绿的 | 加新错误时同步改 `writeErr` + `fmctl` |
| 坑 47 | 任务书写"这处不用改" | 交付后才发现原有行为不是想的那样 | "不用改"也是断言 | 凡说"不用改"，先看一眼现状 |
| 坑 48 | 文档时效性 | 文档说"未实现"，代码其实有了 | 文档读起来很权威 | 拿代码撞；撞出一处 ⇒ 全批重审 |
| 坑 49 | 测试构造错像实现坏 | 误判为 bug 并去改正确的代码 | 两种情况表现一致 | **先打印实现的实际输出，再下结论** |

## 8. 给 agent 的测试规范

### 8.1 派活时 prompt 必须写清

1. **测试文件路径**（精确到文件名）
2. **每条断言的期望值**（不要写"测试一下"，要写"断言 `BySource` 等于 `{custom:1, suricata:1, public:1}`"）
3. **禁止改实现**（纯补测试的任务要明确"不许动 `internal/**` 的非测试代码"）
4. **禁止做变异测试**（很烧步数；变异由 PM 做）
5. **夹具要求**：用 `t.TempDir()`、不依赖仓库真实文件（除非特批）
6. **必须跑的命令**：`gofmt -l .` / `go build ./...` / `go test ./... -count=1`

### 8.2 验收时 PM 必须自己做的（不信 agent 报告）

| 检查 | 为什么 |
|---|---|
| `git status --short` 对授权范围 | agent 会越界改文件 |
| `gofmt -l .` | agent **反复漏跑**（坑 36 / 47 系列，已发生多次） |
| 自己跑测试与端到端命令 | "Success: Yes" 两个方向都会错 |
| 看测试**断言强度** | agent 爱写弱断言 |
| **变异验证**至少一处 | 否则不知道断言是否有守备力 |
| 检查是否有 "未测试的改动" | "测试全绿" ≠ "覆盖了我的改动"（14-1 真实教训） |

### 8.3 常见失败模式与对策

| 失败模式 | 症状 | 对策 |
|---|---|---|
| 零测试交付 | 实现完整、无 `_test.go` | 把"写测试"拆成独立一轮（坑 36） |
| 弱断言 | 全是 `!= nil` / `> 0` | prompt 里给出**精确期望值** |
| 漏 gofmt | `gofmt -l` 报新文件 | PM 兜底修；prompt 里点名"只格式化你改的文件" |
| 测试构造错 | 断言看似合理但触发不到目标分支 | PM 先打印实际输出再判断（坑 49） |
| 越界改动 | 改了未授权文件 | 范围锁 + 事后审计 |

## 9. 新功能测试清单（可直接抄）

```markdown
- [ ] 单元：核心函数每个分支各一条
- [ ] 边界：0 / 1 / 最大值 / 越界 各一条
- [ ] 错误路径：非法输入 / 缺依赖 / 超时
- [ ] 正常基线：正常输入**零异常**（误报基线）
- [ ] 集成：真实环境（DB/FS/进程）真跑一次
- [ ] 可复现：连跑两次，输出完全一致
- [ ] 变异验证：至少一处故意改坏会红，且红在正确位置
- [ ] 回归：`go test ./... -count=1` 全绿，golden 未变
```

## 10. 一句话总结

> **宁可写一条会红的测试，不要写十条永远绿的测试。**
> 判断测试质量的问题只有一个：**"它能抓住什么错误？"** 答不上来，它就是装饰。
