# 模块启停与编译期裁剪（设计草案 v1）

> 状态：**草案，待审批**（2026-10-15）｜ 拟作为**大任务 12**
> 诉求来源：用户提出"**可以选择功能进行编译 / 全部编译，使用时在单独的功能选择界面选择是否启用**"，
> 并明确要 **Web 与 CLI 两个入口共用同一个内核、完成相同的后端行为**。
> ★ 本文所有"现状"都**核对过代码**（`git` 里的实际文件），不是凭印象写的。

---

## 0. 一句话

把现在已经存在的"**声明式清单 + 拓扑排序 + 进程级启停构件**"补齐成一套完整能力：
**清单分级（core/optional）→ 装配期按清单启停 → 运行期按依赖图级联启停（含 drain）→
Web 拓扑图与 CLI 两个入口共用同一套行为 → 构建期按清单裁剪插件二进制**。

## 1. 目标

| # | 目标 | 为什么 |
|---|---|---|
| G1 | **清单分级**：`core`（维持运行的最低集，不可禁用/不可裁剪）与 `optional`（可选功能） | 用户："维持程序运行的最基本模块，绝对不能删" |
| G2 | **运行期启停**：停一个模块时，**按依赖图从最末端到它依次关闭**，不崩、不冲突 | 用户原话 |
| G3 | **功能选择界面（Web）**：读注册信息画 **L0~L3 依赖拓扑图**，可点击查看详情（版本/健康/依赖/影响面）并做启停 | 用户："使用它的都是专业人士，尽可能详细" |
| G4 | **CLI 入口**：无 GUI 的 Linux 也能完整操控（Unix 文件树语义），并逐步长成 **Metasploit 风格内嵌终端**（启动自检 → 提示符 → 自定义命令） | 用户："web 和 cli 是不同的展示形式、不同入口，完成相同的后端行为" |
| G5 | **编译期裁剪**：用 bash + PowerShell 脚本自由选择编译范围，**不需要的模块不参与编译** | 用户："砍体积、砍模块、直接一点"；PM 补充：★ 它更大的价值是**强制解耦**（见 §8.3） |

★ **明确不做**（本大任务）：C/S 分离的多副本启停一致性、插件市场/热更新下载、细粒度权限模型。

### 2.2 ★ 缺口（本大任务要补的）

| # | 缺口 | 说明 |
|---|---|---|
| D1 | **没有 `core` 概念** | 现在任何模块都能被 `enabled=false` 关掉，包括维持运行的那些 |
| D2 | **运行期只能"全停"**：`StopAll` 没有单模块 `Stop(id)/Start(id)/Restart(id)` | 构件都在（状态机 + `Launch` + `UnregisterByModule`），缺编排 |
| D3 | **没有级联停与 drain** | 停 A 时，依赖 A 的模块必须**先**停；在途数据要有机会落地（★ 见 §5 红线） |
| D4 | **没有控制面 API**（HTTP/JSON 或 CLI） | `App` 只有 `Start/Wait/Shutdown`；`health` 只有一个只读 handler |
| D5 | **没有拓扑图界面** | 前端只有"面板注册表"，没有"模块/依赖可视化" |
| D6 | **没有构建期裁剪** | 所有 `cmd/plugins/*` 都会被 `go build ./...` 编译 |
| D7 | **没有架构守卫** | 宿主若 import 了某个可选模块的包，该模块**永远砍不掉**，且**平时看不出来** |

## 3. 三层模型（把用户的诉求拆开）

```
A 编译期裁剪   构建时选择"哪些插件二进制参与编译"          → §8
B 装配期启停   启动时按清单 enabled 装配（★ 已存在）        → §4（补 core 校验）
C 运行期启停   运行中按依赖图级联启停 + drain               → §5
   两个入口：Web（拓扑图/详情/开关）  CLI（文件树/内嵌终端） → §6 §7
```

## 4. 清单规范（在既有 `Descriptor` 上**只加必要字段**）

```jsonc
{
  "id": "modules.detect",
  "name": "行为检测",
  "version": "0.1.0",
  "layer": "L2",
  "core": false,                  // ★ 新增：true = 不可禁用、不可裁剪（缺它则拒绝启动）
  "enabled": false,               // 已有：装配期开关
  "binary": "detect",             // 已有：插件二进制名（编译期裁剪用）
  "depends": ["modules.rule"],    // 已有：显式依赖（模块 id）
  "provides": ["detect.feature", "alert.lifecycle"],  // 已有：能力名
  "injects": ["alert.lifecycle"], // 已有：需要的能力名（展开为隐含依赖，宿主已有实现）
  "http_base": "/api/detect"      // 已有：HTTP 前缀（控制面/前端路由用）
}
```

### 4.1 语义约定（★ 一条都不能含糊）

1. **依赖方向**：`provides` 是**能力名**；`depends`（模块 id）与 `injects`（能力名 → 提供者模块）
   **都表示"我需要它"** ⇒ 依赖图的边是 **提供者 → 消费者**（提供者必须先启、后停）。
2. **`layer` 只用于展示分组**，★ **绝不用于决定启停顺序** ——
   同层内部同样有依赖（用户原话"从末尾层到它依次关闭"是**直觉正确、但不充分**，
   真正的顺序是**依赖图的反向拓扑序**）。
   ★ **实际层级只有 L0~L3**（12-1 实测核对 `pkg/plugin/manifest.go`）：
   `L0 内核`（宿主进程内，**不作为插件**）/ `L1 基础功能` / `L2 具体功能` / `L3 用户扩展`；
   清单里目前只用到 L1/L2。前端拓扑图按这四层分组即可（**没有 L4**）。
3. **`core: true` 的模块**：不可禁用、不可裁剪；**控制模块自己必须是 core**；
   启动期若发现任何 core 模块缺失/未启用 ⇒ **拒绝启动并明确报错**（不许静默降级）。

### 4.2 校验规则（新增一个 `registry` 自检）

| 规则 | 现状 | 本任务 |
|---|---|---|
| 缺能力提供者 | ✅ 已有 `ErrUnresolvedDep` | 复用 |
| 依赖成环 | ✅ 已有（拓扑排序失败即报） | 复用 |
| **core 模块缺失（清单里没有）** | ✗ | ★ 新增：**拒绝启动** |
| ★ **core 与 `enabled` 的关系**（见 §4.3） | ✗ | 新增：core **允许** `enabled=false`（只是自检里提示），**不允许**从清单/构建里消失 |
| **核心模块依赖了非核心模块**（`depends`/`injects` 落到可选模块上） | ✗ | ★ 新增：**报错**（核心依赖可选 = 核心不再是最低集，且停那个可选模块会拖垮核心） |
| 层号与依赖方向不一致（L3 依赖 L1 却声明 L2 等） | ✗ | 新增：**警告**（不阻塞） |

### 4.3 ★ `core` 与 `enabled` 是两件事（2026-10-16 修正）

| 字段 | 管什么 | 后果 |
|---|---|---|
| `core: true` | **构建与清单层面**：不可裁剪、不可从清单删除 | 清单里缺任一 core ⇒ **拒绝启动**；构建期裁剪必须包含 core（12-5 校验） |
| `enabled` | **本次装配**：这次运行要不要启动它 | core 模块 `enabled=false` ⇒ **允许**（自检里列一条提示"核心模块未启用"），**不阻塞启动** |

★ 为什么这么拆：修正前的草案写"core 被 `enabled=false` ⇒ 拒绝启动"，而 `modules.capture`
**当前就是 `enabled=false`** ⇒ 会把服务直接启不起来 ✗。**"绝对不能删"指的是构建/清单层面**，
与"这次跑不跑它"是两件事。
★ 但**运行期的 `Disable` 仍然拒绝停 core 模块**（§5.1 第 1 条）—— 那是运行期语义，不受此影响。

## 5. 级联启停（★ 本设计最需要谨慎的部分）

### 5.1 关闭顺序（算法）

```
Disable(target):
  1. 若 target 是 core            → 拒绝（返回明确错误）
  2. 求"依赖闭包"：所有**直接或间接依赖 target** 的模块集合 D（沿"提供者→消费者"正向走）
  3. 校验 D 中是否有 core          → 有则拒绝（"停它会连带停掉核心模块 X"）
  4. 顺序 = 反向拓扑序(D) 后接 target      // 先停最末端消费者，最后停 target
  5. 逐个执行 StopOne(id)（见 5.2），任一失败 ⇒ 停止级联并**如实报告已停/未停**
  6. 成功后把 target 的 enabled 落盘（可选：写回清单或写运行时状态）
```

★ 复用既有能力：`registry.TopologicalSort()` 给出全序，**取其子图 + 反向**即得关闭序；
`pluginhost.Manager` 已有状态机与 `StopAll` 的逆序先例可照抄。

### 5.2 单个模块的停止（`StopOne`）—— ★ 红线：**先停消费者、给 `Stop()` 超时、超时如实记账**

★ **2026-10-16 修正措辞**（12-3a 落地时与实现对表）：本文件原写"**先断供给** → drain → 停进程"，
在 go-plugin（**每模块一个独立进程**）形态下这个说法会误导：
- **"先断供给"其实就是"先停消费者"** —— 消费者停了，就没有人再从这个模块取数据；
  这正是级联顺序（**反向拓扑序：先停最末端消费者、目标最后**）所做的事，
  **不需要额外的"主动断流"**（那需要模块间数据流的知识，属更大的话题）。
- **"drain" 在这里 = 给模块自己的 `Stop()` 一个超时**：模块负责把在途数据落地（`Stop()` 是它的优雅停止），
  **超时未完成则强杀，并如实记账**（"模块 X 停止超时，未能确认在途数据已落地"）。

```
StopOne(id):
  1. 状态检查（只允许 started → stopping → stopped）
  2. ★ 先由级联保证"消费者已停"（见 §5.1 的顺序）
  3. ★ 调 module.Stop()（模块的优雅停止，负责把在途数据落地）——**带超时**
  4. 超时 ⇒ 强杀（client.Kill），并**如实记录**"未能确认在途数据已落地"
  5. bridge.UnregisterByModule(id) 回收可逆副作用（服务注册 / HTTP 路由）
  6. 置 stopped；全过程写入审计
```

★★ **为什么这条是红线**：10-6 已经踩过一次"**退出路径丢告警**"（带缓冲 channel 里的告警在 `Close` 顺序不当
时被丢掉）—— ★ **启停会把它原样重演**：capture/detect 被停时，手上的包/告警必须有地方去。
判据：**"停完之后，能不能证明没有数据凭空消失？"**（要么落地、要么**如实记录未能确认**）。

### 5.3 启动顺序

与关闭相反：**正向拓扑序**（提供者先起）；核心模块**先起**且**失败即拒绝启动整个进程**。

## 6. 控制面（★ 唯一行为实现 + 双入口）

### 6.1 内核服务层（唯一一份行为实现）

```go
// internal/kernel/modulecontrol（新包，名字待定）
type Service interface {
    List(ctx) ([]ModuleView, error)        // 含 layer/core/enabled/state/version/health/http_base
    Graph(ctx) (Graph, error)              // 节点 + 依赖边 + 能力边（★ 影响面由后端算）
    Impact(ctx, id) (Impact, error)        // 停它会影响谁（含 core 冲突判定）
    Enable(ctx, id, opts) (Result, error)
    Disable(ctx, id, opts) (Result, error) // 级联（§5）
    SelfCheck(ctx) (SelfCheck, error)      // 核心齐备/环/缺提供者/层号一致性
}
```
★ **Web 与 CLI 都只调这一层**（用户要求"完成相同的后端行为"）——
绝不允许 CLI 与 Web 各写一套逻辑（那样行为迟早漂移）。
★ **命令行优先**：CLI 与 HTTP 是同一层的两个薄壳；`fmctl` 在无 GUI 环境必须能做全部事。

### 6.2 接口与命令（草案）

| 动作 | HTTP | CLI |
|---|---|---|
| 列表 | `GET /api/modules` | `modules` / `ls` |
| 详情 | `GET /api/modules/{id}` | `show modules.detect` |
| 依赖图 | `GET /api/modules/graph` | `tree` / `tree L2` |
| 影响面 | `GET /api/modules/{id}/impact` | `impact modules.detect` |
| 自检 | `GET /api/modules/selfcheck` | `selfcheck` |
| 启停 | `POST /api/modules/{id}/enable|disable` | `enable <id>` / `disable <id>` |

### 6.3 安全与可审计（★ 安全产品必须有）

1. **鉴权**：复用 `modules.auth`（清单里已有）；控制面默认**只监听回环**，除非显式放开；
2. **审计**：每次启停写一条审计（谁 / 何时 / 对谁 / 结果 / 影响了哪些模块）；
3. ★ **危险操作先给影响面**：`disable` 默认**先返回影响面并要求确认**
   （CLI：交互确认或 `--yes`；HTTP：`?dry_run=1` 先看，再 `?confirm=<token>`）——
   ★ 一个手滑就把采集停了，是这套功能最现实的危险。

## 7. 前端（静态拓扑图 → 详情 → 启停；拖拽后补）

1. **数据来源**：只消费后端 `Graph/Impact/List/SelfCheck`（★ **影响面绝不前端自己算**，
   否则界面提示与真实级联行为会不一致）；
2. **展示**：按 `layer`（**L0~L3**）**分层摆放**的静态拓扑图，节点显示 名称/版本/状态色（健康）/core 标记；
3. **交互**（本阶段）：点击节点 → 侧栏详情（版本、健康、提供/依赖的能力、**"停它会影响谁"**）→ 启停按钮
   （含二次确认）；**拖拽/自由布局作为增强项后补**（用户已定：先静态拓扑）；
4. ★ **panel ↔ module 的映射**：面板 manifest 增加 `moduleId?: string`，
   shell 装配时**只显示对应后端模块已启用的面板**（前端现在是"编译进去、全量注册"的，
   必须由后端状态来过滤，否则会出现"模块停了、界面入口还在"的假象）。
5. 图渲染实现自选（先用手写 SVG/Canvas 分层布局；节点多了再考虑引入图形库）。

## 8. 编译期裁剪（构建脚本 + 架构守卫）

### 8.1 脚本接口（bash + PowerShell，两个平台等价）

```bash
scripts/build-modules.sh        # Linux/macOS（无 GUI 也能用）
scripts/build-modules.ps1       # Windows
  --all                 构建全部插件（默认）
  --core-only           只构建 core 模块
  --modules=a,b,c       只构建列出的模块（自动带上它们的**运行时依赖闭包**）
  --list                只打印"这次会构建什么"，不构建
  --out=dist/plugins    产物目录
```
产出：每个选中模块一个插件二进制 + **`build-manifest.json`**（本次构建包含哪些模块、版本、git commit，
供运行期自检与前端展示"这份构建带了什么"）。

### 8.2 与清单的关系

脚本**读的是同一份清单**（`registry/backend-modules/*.json` 的 `binary` 字段），
★ **不另建一份构建配置**（两份配置必然漂移）。

### 8.3 ★ 架构守卫（我认为这才是编译期裁剪最大的价值）

**问题**：宿主（`cmd/server`）若直接 import 了某个可选模块的包，那个模块就**永远砍不掉**，
而且**平时完全看不出来** —— 等到真要裁剪时才发现为时已晚。

**做法**：
1. **检查脚本**：用 `go list -deps ./cmd/server` 求出宿主依赖闭包，断言其中**不含可选模块的包路径**；
   违反 ⇒ 构建失败并指出"谁 import 了它"；
2. **保留 `parse-cli` 等独立入口**的自主性（它们本来就直接依赖模块，属于"全量构建"入口）；
3. 与"可选接口 + 能力探测"的既有做法（11-7b 的 `PacketFlowQuerier`）配合：
   ★ **扩展能力优先用可选接口，而不是往公共接口加方法**（加方法会连带所有实现者 + RPC 协议）。

## 9. 分阶段与验收判据

| 阶段 | 内容 | 验收判据（必须可测） |
|---|---|---|
| **12-1 清单分级与自检** | `core` 字段 + 校验规则（§4.2）+ `selfcheck` 服务层 | ① 缺 core ⇒ **拒绝启动**并有明确错误；② 核心依赖可选 ⇒ 报错；③ 环/缺提供者 ⇒ 报错；④ 自检输出稳定（golden） |
| **12-2 控制面服务层 + CLI** | §6.1 服务层 + `fmctl`（文件树语义，先不做内嵌终端） | ① 无 GUI 环境完成 list/show/tree/impact/enable/disable；② **Web 与 CLI 行为一致**（同一服务层，加一致性测试） |
| **12-3 运行期级联启停** | `StopOne/StartOne` + 反向拓扑级联 + **drain/超时** + 审计 | ① 停 A ⇒ 依赖 A 的按**反向拓扑序**全停；② core 冲突 ⇒ 拒绝且**不动任何模块**；③ ★ **drain 测试：停的过程中在途数据不丢**（或如实报告丢了多少）；④ 中途失败 ⇒ 如实报告已停/未停 |
| **12-4 前端拓扑图** | 静态分层拓扑 + 详情 + 影响面 + 启停（二次确认）+ 面板按模块过滤 | ① 图与后端 `Graph` 一致；② 停某模块后面板入口消失；③ core 节点不可点"停用" |
| **12-5 构建裁剪 + 守卫** | §8 脚本 + `build-manifest.json` + 架构守卫 | ① `--modules=a` 只产出 a 及其依赖；② 运行期自检能发现"清单里有但二进制缺失"；③ 守卫能**抓出**宿主 import 可选模块（故意造一次违规验证） |

## 10. 风险与红线

| 风险 | 对策 |
|---|---|
| ★ **停机丢数据**（10-6 的教训重演） | §5.2：先断供给 → drain（带超时）→ 停止；**丢了多少必须如实记账** |
| ★ **只按层号排序**导致顺序错、出现"边停边用" | 顺序一律用**依赖图反向拓扑序**；`layer` 只做展示 |
| ★ **控制面变成后门** | 默认只监听回环 + 鉴权 + 审计 + 危险操作二次确认 |
| ★ **前端自己算影响面**，与后端不一致 | 影响面**只由后端算**，前端只渲染 |
| ★ **宿主耦合可选模块**，裁剪名存实亡 | §8.3 架构守卫（CI 强制） |
| 状态持久化位置未定（清单 vs 运行时状态 vs DB） | 见 §11 待拍板 |
