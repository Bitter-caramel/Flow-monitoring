> 版本：v2（复用策略定稿）

> 状态：规划，尚未实现
> 配套：《架构.md》（总体分层）、《插件与模块.md》（插件机制）、《解析器.md》（解析层）、《规则翻译器.md》（规则接入层）
>
> **v2 变更**：新增 §2「技术选型：自研 vs 复用红线」；解析层 decoder 由自研改为**复用 gopacket**；检测规则格式改为**兼容 Suricata**（不自创 schema）；前端图表改为按需引入。

## 0. 一句话定位

网络安全流量检测平台（IPS / IDS），部署在**服务器本机**或**监听服务器流量的机器**上，按「服务 / 资产」做定制化检测，实时检测攻击流量、精准收集攻击流量、复原攻击链。

---

## 1. 核心原则：数据驱动，不改代码

定制化**不靠改代码**，而是把"定制"全部变成**数据**：

> 代码只写"引擎"（怎么检测、怎么匹配、怎么分发事件），管理员通过 webUI / CLI 改**数据**（资产清单、规则库、映射），改动即时生效。

这本质是「everything is a plugin」在**规则/资产数据层**的落地。

---

## 2. 技术选型：自研 vs 复用红线

> 项目目标不是毕设，是**开源「六边形战士」**（未来考研/求职的王牌）。因此原则是：
> **把"苦力活"外包给社区，把全部精力砸在"能形成差异化"的地方。**

### 2.1 唯一判断标准

> 这件事是不是「社区已经解决、且抄不走你的差异化」？
> **是 → 复用；能形成差异化 → 自研。**

### 2.2 红线表

| 类别 | 模块 | 决策 | 理由 |
|---|---|---|---|
| 🟢 复用 | 协议解码 (decoder) | **换 gopacket**（旧 decoder 移到 `Learn-Project`） | 解码是苦力活；且**不同解码器结果不同，会污染下游**，必须标准化 |
| 🟢 复用 | 抓包采集 (capture) | gopacket afpacket / raw socket | 纯系统调用层，零自研价值 |
| 🟢 复用 | 规则内容 | **Suricata 规则集**（运行时加载，**不内嵌**） | 社区几十万条签名，内容成本远大于引擎成本 |
| 🟢 复用 | 前端图表 | **按需**引入 ECharts / React Flow | 纯展示层；先自绘简单图，复杂图（拓扑/时间线）再引 |
| 🔴 自研 | 检测引擎 | 自研（热路径集成 + 定制化） | 与自研资产模型/解析层耦合，是差异化 |
| 🔴 自研 | 态势 / 处置 / 攻击链 / 告警 | 自研 | **蓝队闭环——项目唯一差异化**，不是"轮子" |
| 🔴 自研 | analyzer / 流聚合 | 已落地，保留 | 检测的数据基础，与定制化强耦合 |
| ⚪ 保留 | pcapng reader | 保留自研 | 文件容器层，非苦力活，已落地 |
| ⚪ 保留 | eventbus | 保留（进程内 pub/sub） | 已论证是正确的最小实现；未来拆多机再评估 NATS |
| ⚪ 保留 | PostgreSQL | 保留，预留 ClickHouse 适配器 | 中小规模够用，靠 storage 接口演进 |

### 2.3 许可证注意

- **Suricata 规则集是 GPL**：只**运行时加载**、**不内嵌**进二进制，避免许可证污染。
- gopacket / ECharts / React Flow 均为 **BSD / Apache-2.0**，可自由使用。

### 2.4 为什么 decoder 必须换（比"省维护"更硬的理由）

不同解码程序的**解码结果不一样**（字段取值、边界处理、异常容忍度）。自研 decoder 一旦和社区标准有细微差异，就会**污染后续的聚合与检测**——检测建立在解码字段上，字段错了，检测就是错的。所以换 gopacket 不只是省维护，是**解码结果标准化**。

## 3. 三层数据模型

### 3.1 资产清单（Asset）—— "端口 / 服务列表"

自动发现 + 人工标注混合，字段如下：

| 分组 | 字段 | 来源 |
|---|---|---|
| 基础 | 端口号、协议(TCP/UDP)、监听地址（0.0.0.0 还是 127.0.0.1，决定是否对外暴露）、PID | 自动发现 |
| 进程 | 程序名、程序完整路径、启动命令、启动时间、所属用户 | 自动发现 |
| 服务识别 | L7 协议(HTTP/HTTPS/SSH/MySQL/Redis…)、服务软件 + 版本(nginx/1.18.0)、banner 指纹 | 自动/半自动 |
| TLS | 证书 CN、颁发者、有效期、是否自签/弱签名 | 自动（若 HTTPS） |
| 人工标注 | 描述（给客户/管理员看）、业务类型/用途、负责人/所属系统、分组标签、备注 | 人工 |
| 状态 | 运行中/已停、连接数、流量统计、最近活跃时间 | 自动 |

### 3.2 规则库（Rule）—— "防范类型"大列表

**声明式**定义，按分类树组织（每类下挂一批具体攻击）：

```
Web      → SQLi / XSS / SSRF / SSTI / 文件上传 / 目录遍历 / 命令注入 / XXE / CSRF / 反序列化 …
Pwn      → 栈溢出 / 堆溢出 / 格式化字符串 / 整数溢出 …
扫描器   → nmap 脚本特征 / 各漏扫指纹 …
协议异常 → 畸形包 / 异常字段 …
凭据     → 明文密码 / 弱口令 …
后渗透   → C2 信标 / 隧道 …
```

每条规则字段：**名称 / 分类 / 检测特征（流量签名）/ 严重度 / 说明 + 参考（CVE、ATT&CK、漏扫脚本名）/ 是否默认启用 / 来源（内置 · Suricata 导入 · 自定义）**。

> **来源**是重点：规则的**内容**主要靠**导入 Suricata 规则集**（§4.3），而不是从零手写。

### 3.3 映射（Asset ↔ Rule 多对多）

每个资产（端口/服务）关联一组启用的规则。webUI 列表支持**单个 / 批量**勾选。

**存储**：资产 + 映射 → **PostgreSQL**；规则库 → 内置 `go:embed` JSON + 导入的 Suricata 规则（存 DB，运行时加载）。

## 4. 检测架构

### 4.1 三层分层

| 层 | 干什么 | 现状 |
|---|---|---|
| 解析层 | 包 → 字段 → 流（"看懂流量"） | decoder **换 gopacket（复用）**；analyzer/流聚合**保留自研** |
| 检测层 | 流/包特征 → 匹配规则 → 判断攻击 | **自研引擎 + 兼容 Suricata 规则格式** |
| 内容层 | 还原出的文件/二进制 → 匹配恶意模式 | **后期接 YARA** |

**本层不做日志检测**（不做 SIEM / 主机日志），只做**网络流量筛查**。因此 Sigma（日志检测规则）**不在范围内**。

### 4.2 声明式检测引擎（自研）

- 检测引擎是**热路径的一部分**，和监听/解析/聚合在**同一进程**内（见 §5.1）。
- 规则是**数据**：加规则 = 导入/加一条数据，不改代码。
- 覆盖漏扫 / Web / Pwn 等**网络层流量特征**（URL 路径、UA、payload 模式、连接速率、时序）。

### 4.3 规则格式：兼容 Suricata，**不自创**

> **禁止先发明自己的规则 schema、再等社区来适配你。**

- **事实标准用 Suricata 规则格式**（社区几十万条现成签名，ET Open 等规则集免费）。
- 自研一个 **「规则翻译器」**，把 Suricata 规则导入为内部可执行格式。
- **`gonids` 只是翻译器的一个可选零件**（它不稳定：Google 仓库半死不活、Suricata 语法持续演进），因此翻译器要设计成**可替换、可扩展的微型架构**——详见《规则翻译器.md》。

### 4.4 为什么接 YARA、不接 Suricata 引擎

- **不接 Suricata 引擎**：它是"检测层"，内部自带一套解析栈，和我们自研的解析层**重复**；接它 = 引入重量级依赖。**但它的规则格式要兼容导入**（§4.3）。
- **接 YARA（后期）**：它是"内容层"（文件/二进制模式匹配），和"网络流检测"**互补不重复**。等做"从流量还原文件、检测恶意样本"时再接。

## 5. 事件总线与"线"（事件流设计）

### 5.1 热路径 vs 冷路径

```
【热路径 · 一个进程】监听 → 解析 → 聚合 → 检测
   每包/每流都要碰，进程内函数调用 + channel 传递，绝不跨进程、绝不进事件总线。

【冷路径 · 可跨进程】告警 / 态势 / 处置 / 攻击链 / 前端
   检测命中才触发，低频，走事件总线。
```

- **一个进程内可以有多个功能模块**（监听/解析/聚合/检测各自是 Go 包/函数），通过函数调用协作。
- **原始流量走进程内专用 channel**（像流水线传送带），只有"检测命中了"这种低频结论才进事件总线。

### 5.2 事件线清单（单一总线 + 多主题）

"线" = 事件总线上的**主题（topic）**。一套总线基础设施，挂多条主题线，按**事件类型**划分、按**关键/监控**分级：

| 线（主题） | 生产者 | 消费者 | 性质 | 可靠性 |
|---|---|---|---|---|
| `detect.feature` | 检测引擎 | 态势、攻击链 | 检测发现 | 🔴 关键·不可丢 |
| `situation.level` | 态势引擎 | 处置、告警、攻击链、前端 | 态势变化 | 🔴 关键·不可丢 |
| `alert.lifecycle` | 告警模块 | 前端、邮件、导出 | 告警状态 | 🔴 关键·不可丢 |
| `disposal.audit` | 处置引擎 | 审计、前端 | 处置审计 | 🔴 关键·不可丢 |
| `attackchain.evidence` | 攻击链 | 案件、前端 | 证据链 | 🔴 关键·不可丢 |
| `capture.health` / `metric` | 采集/各模块 | 前端监控、运维 | 水位/性能 | 🟡 尽力·可丢 |

**关键区别**：前 5 条"证据/决策类"满了要背压（宁慢不丢）；最后 1 条"监控类"满了直接丢 + 计数（丢了没事）。

### 5.3 事件流图（一次端口扫描的完整链路）

```
检测引擎 ─投─▶「detect.feature」─收─▶ 态势引擎 ─投─▶「situation.level」
                                               ├─收─▶ 告警模块 ─投─▶「alert.lifecycle」
                                               └─收─▶ 处置模块 ─投─▶「disposal.audit」
（攻击链同时订阅 detect.feature 与 situation.level，记录证据链）
```

要点：
1. **线按"事件类型"串链**，一个模块可同时是"收信方"和"投信方"（如态势：收 detect.feature、投 situation.level）。
2. **"告警后的动作"（发邮件/封IP）不是线**，是模块收信后自己干的事；只有"动作的结果"才投审计事件。
3. **"提升监听等级 / 记录攻击链"不是新线**，就是 detect.feature → situation.level → attackchain 这条链。

## 6. 部署形态

### 6.1 一套核心 + 双前端

- **一套 Go 核心**：检测引擎、资产发现、规则匹配、告警、事件总线，全部在核心里。
- **两个入口**：React webUI（有屏环境）+ CLI（无屏 Linux）。
- GUI 和 CLI 是"同一套核心的两张皮"，不是两套系统。

### 6.2 编译选项（build tags）

| 编译 | 产物 | 场景 |
|---|---|---|
| 默认 `go build` | webUI + CLI + 核心全量 | 带 GUI 的机器 |
| `-tags headless` | 核心 + CLI（不嵌前端静态文件，二进制小几 MB） | 无 GUI 服务器 |

> CLI 命令集代码很小，主要就是"全量 vs headless"两档；"只要 webUI 不要 CLI"技术上也行，按需加。

### 6.3 CLI（后置，只定方向）

命令集（未来）：`status` / `assets list|show|set` / `rules enable|disable` / `monitor start|stop` / `alerts` / `config apply|export`。输出默认人类可读，加 `--json` 出机器可读。**现阶段不实现，专注 webUI。**

### 6.4 前端图表（按需引入）

- 图表是**纯展示层**，与后端检测性能、数据流**完全无关**。
- **先自绘**简单图（协议占比、端点表格），**不提前背负依赖**。
- 等要做**力导向拓扑、攻击链时间线**等复杂图时，再接 **React Flow / ECharts**（Apache-2.0），并自行封装一层组件以屏蔽底层 API。

## 7. 监听与数据源

### 7.1 实时监听 + 回放，共用同一引擎

| 模式 | 数据源 | 用途 |
|---|---|---|
| 实时监听（生产） | 网卡 / 镜像口持续抓包 | 边抓边检测，实时出结果 |
| 回放（测试/离线） | pcapng 文件按时间顺序重播 | 开发测试 / 离线取证 / 回归 |

**两者同一个检测引擎，只换数据源**（网卡 vs 文件）。实时抓包直接用 **gopacket**（§2.2）。

### 7.2 部署形态（两种都支持）

- **主机侧**：部署在服务器上，抓本机网卡。
- **旁路**：部署在另一台机器，服务器把流量镜像（SPAN/TAP）过来分析。

### 7.3 处置与监听解耦

封 IP 等处置动作**作用在服务器（或防火墙）上**，与监听位置无关。所以"监听主体"和"处置主体"解耦：监听在分析机或本机，处置指令下发给服务器。对应 `disposal`（处置引擎）独立成模块。

**现阶段**：静态 / 回放优先，动态监听后置。

## 8. 资产发现

### 8.1 最终形态：一键自动发现

webUI 加一个「自动发现」按钮，管理员点一次，程序跑一次：检测开放端口、服务、指纹、进程、TLS 等，回填资产清单。

### 8.2 现阶段：手动录入

先做 **webUI 手动录入资产 + 选择防范类型**，跑通闭环；自动发现程序和按钮后置。

## 9. 短期开发路线图

1. **换 decoder**：gopacket 替换自研 decoder，写「gopacket → datamodel.Packet」适配层，**analyzer 一行不改**；旧 decoder 代码搬到 `Learn-Project`。
2. **规则翻译器**：设计可替换的微型架构，先把 Suricata 规则导入为内部格式（详见《规则翻译器.md》）。
3. **检测引擎**：内容型（逐包）+ 行为型（逐流）匹配，按资产筛选规则。
4. **webUI：资产手动录入 + 防范类型多选**：资产 CRUD + 规则多选 + 映射落库。
5. **回放闭环**：pcapng → 解析 → 聚合 → 检测 → 事件（detect.feature）→ 告警，端到端跑通。
6. **后置**（按需逐步）：自动发现、实时监听、CLI、YARA、图表库、处置(disposal)、态势(situation)。

- 本规划是《架构.md》的**下钻**：解析层/插件机制已存在，本规划聚焦"检测层 + 资产/规则数据模型 + 部署形态"。

  2. 协议解码层由自研改为复用 gopacket（旧代码移出项目，存入 `Learn-Project` 供学习）。
