# 架构说明

本文说明流量分析平台的整体架构：怎么分层、模块怎么组织、数据怎么流动、检测态势怎么闭环。

## 1. 设计原则

| 原则 | 含义 |
|---|---|
| 内核最小化 | 内核只放"几乎所有模块都要用、且极少变动"的能力；能被替换的功能一律不进内核 |
| 契约第一 | 模块之间只通过公开接口（契约）通信；内核内部实现随便优化，只要契约不变 |
| 一切可替换 | 不追求字面 everything is plugin，追求 everything is swappable：内置模块与第三方插件走同一套契约 |
| 先模块化，后插件化 | 先用"清晰模块"形态磨接口，接口稳定后再开放为插件 SDK |
| 重解析在后端 | 浏览器只做渲染与交互，不做大型抓包文件的深度解析 |
| 检测分级 | 态势分级不是 UI 概念而是架构状态：级联决定资源投入、告警强度、处置力度 |
| 处置可控 | 处置动作分强度，默认"先记录后执行、先模拟后真实"；真实封禁必须有显式开关与冷却 |
| 自保护优先 | 监测程序自身不得被打垮：任何检测/处置路径都带水位线、限流与降级出口 |

## 2. 总体架构

```
浏览器（React + TS 薄壳）
   │  REST / WebSocket
   ▼
Go 宿主进程 server
   ├─ L0 内核（进程内，写死）
   │   bootstrap · registry · pluginhost · transport(网关) ·
   │   eventbus · config · logging · health · storage · datamodel
   │
   ├─ 宿主桥（net/rpc）：Config / Log / Publish / Poll /
   │   RegisterService / LookupService / RegisterHTTP / 存储索引
   │
   └─ 模块进程（每个模块独立二进制，go-plugin/RPC 挂载）
       importer · query（真进程；其余 9 个待补，detect/rule 是内嵌库）
```

### 2.1 三块现状（2026-10-17 核实）

| 块 | 状态 | 组成 |
|---|---|---|
| A 离线回放 | ✅ 已实现 | pcapng 文件 → `cmd/parse-cli` → `internal/hotpath`（归流 → 重组 → 检测）→ 告警打印 |
| B 宿主 + 插件层 | ✅ 已实现 | `cmd/server`（L0 内核）→ registry 拓扑排序 → 启动模块进程（现只有 importer / query）→ 网关反代 + 事件总线 |
| C 实时监测 | ❌ 未接 | 网卡 / 镜像口 → 采集（未实现）→ hotpath → 事件总线 → situation / alert / … |

- `cmd/server` **目前没有 import** `internal/hotpath`，即宿主进程还没跑检测；
- 实时采集（`modules.capture`）**一行代码都没有**；
- 所以「检测在热路径进程内」目前只在 A 块成立，是**设计目标而非既成事实**。

## 3. 分层模块全表

### L0 内核（宿主进程内，非插件）

| 模块 | 职责 |
|---|---|
| bootstrap | 总开机：读配置 → 建基础设施 → 读注册表 → 按拓扑序启动模块进程 |
| registry | 模块登记本：加载 json 清单、拓扑排序、依赖校验 |
| pluginhost | 插件插座：宿主桥（Bridge）+ 模块进程管理（Manager） |
| transport | 接待窗口：HTTP 中间件 + 静态托管 + 网关反代 + WebSocket |
| eventbus | 广播喇叭：进程内 pub/sub，模块间解耦通信 |
| datamodel | 数据字典：包 / 流 / 会话 / 威胁对象等统一模型 |
| config / logging / health / storage | 读配置 / 记日志 / 体检 / 存储接口标准 |

### L1 基础功能（挂在地基上的可替换能力）

| 模块 | 职责 |
|---|---|
| parse | 解析内核：pcapng 读取 + L2/L3/L4/L7 解码 |
| store | 存储实现：PostgreSQL（实现 storage 接口） |
| packetstore | 原始数据包文件仓库（dir/{id}.bin + SHA256 + 原子写） |
| importer | 进货口：上传抓包文件 → 检查 → 切块 → 送解析 → 入库 |
| auth / capture / ioc | 认证权限 / 采集抽象 / 黑白名单（已注册，待补） |
| rule | 规则统一模型（**内嵌库（无独立进程）**） |

### L2 具体功能

| 模块 | 职责 |
|---|---|
| query | 查询窗口：REST 分页查询 captures / packets（已跑通的插件样板） |
| detect | 行为检测（**内嵌库**，随宿主进程运行，无独立进程）：扫描 / 爆破 / 信标等，产出 detect.feature 事件 |
| situation | 态势引擎：按源 IP 聚合评分，三级态势升降级，产出 situation.level |
| disposal | 处置引擎：态势映射动作矩阵，默认模拟，真实封禁显式开关 |
| alert | 告警：去重 / 抑制 / 推送 |
| attackchain | 攻击链：把零散证据按时间串成攻击过程 |
| case / export | 案件档案 / 报告导出 |

### L3 用户扩展

自定义态势规则包、处置动作插件、报告模板等。

## 4. 插件 / 进程模型

- 内核（L0）不 import 任何业务模块，只在启动时读 `registry/backend-modules/*.json`。
- **除内嵌模块（`modules.detect`、`modules.rule`）外**，每个模块是 `cmd/plugins/<name>` 编译出的独立二进制，通过 hashicorp/go-plugin（net/rpc）与宿主通信，崩溃不拖垮宿主。内嵌模块以库形式链接进宿主，不产出二进制。
- 模块间不直连：只通过事件总线（Publish/Poll）和服务注册/注入（provides/injects）通信。
- 模块不直连数据库：存储访问经宿主桥（Capture*/Packet*），原始抓包文件（pcapng）由模块进程自己读写本地磁盘。
- 可替换：换实现 = 换二进制 + 改 json 的 `binary`；换服务提供者 = 换 `provides` 的那个模块。
- 清单里 `"inprocess": true` 的模块即内嵌模块，`fmbuild --list` 会显示 `skip:inprocess`。

详见 [`docs/插件与模块.md`](插件与模块.md)。

## 5. 数据流

```
静态：导入 pcapng → importer 切块 → parse 解码（包/流/会话对象）
      → packetstore 存原始文件 + store 存元数据 → query 查询 → 前端展示

动态（目标）：采集/回放 → 解析 → 特征事件流（detect.feature）
      → situation（IP 聚合评分 → 三级态势 → 升降级）
      → disposal（态势映射处置动作，默认模拟）
      → alert / 前端 WS 实时推送
```

## 6. 态势闭环（核心功能）

对象模型为**双层聚合**：

- **流对象**（五元组粒度）：由解析内核产出，数量大、生命周期短，只做统计不过度留痕。
- **IP 聚合对象 Subject**：态势感知的主对象，聚合到"源 IP ↔ 保护目标"维度，带评分、状态、证据与冷却。

三级态势（对外呈现三级 + 危急档）：

| 等级 | 语义 | 系统行为 |
|---|---|---|
| 正常 | 无攻击特征 | 仅统计，Subject 冷却回收 |
| 关注（默认） | 有可疑行为 | 保留证据、不自动处置 |
| 攻击（升级） | 确认攻击 | 攻击链归档、告警、按策略处置（先模拟） |
| 危急（快速升级） | 大规模攻击 / 自保护 | 批量封禁（分批、背压）、降采样 |

升降级带**滞回 + 观察窗口 + 衰减 + 冷却**，防止误判导致的抖动。处置动作默认 sim 模式（只记录不真封），真实封禁按强度分级开关并带回滚清单。
