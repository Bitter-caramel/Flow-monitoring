## 0. 锚点（判断一切任务该不该做的唯一标准）

> **这是一个 IDS/IPS：实时监测攻击流量 → 精准收集攻击流量 → 复原攻击链。**

**三条硬指标**（用户打开产品时，应该能完成其中至少一件）：

1. **能看见攻击** —— 有流量进来时，产出可解释的告警（规则 ID / 命中位置 / 证据）
2. **能持续看见** —— 不需要手动跑命令行，服务常驻、告警持续产出、界面能看到
3. **能应对** —— 从告警到评级到处置到串链，形成闭环

**不在以上三条上的工作，一律视为"支撑性工作"，不能连续做两轮。**

### G. 能看懂加密流量（TLS 解密）⬜

> **为什么必须有**：现实流量里 HTTPS 占绝大多数。不解密，检测只能看到 SNI 与证书，
> 看不到请求体/URI/UA——而这恰恰是 Web 攻击特征所在。
> **这是一项大工程**，但它决定"能不能真正看见攻击"，因此单独立方向，不塞进 C。

- **G1 密钥来源（先做最实用的一种）**
  - `SSLKEYLOGFILE` 格式解析：`CLIENT_RANDOM <client_random> <master_secret>`
  - 关联方式：TLS `ClientHello` 的 `client_random` → 该连接的会话密钥
  - 其它来源（仅记录、先不做）：RSA 私钥（只对 TLS_RSA_* 套件有效，现代已淘汰）、
    eBPF 钩明文（需 root，属 C 方向变体）
- **G2 TLS record 解密**
  - TLS 1.2：AES-GCM / AES-CBC + HMAC-SHA256(384)
  - TLS 1.3：AES-GCM / CHACHA20-POLY1305；密钥由 HKDF 从 handshake secret 派生
  - 解密后把明文交回 L7 解析（HTTP/2 需先解帧；HTTP/1.1 直接可解析）
- **G3 归流期挂密钥**
  - 归流阶段识别 TLS 连接，把 `client_random` → 解密器 绑定到该流
  - ★ **解密失败必须可观测**：不能像"静默失效"那样返回空（见踩坑 15/23 的教训）
- **G4 合规与边界（写进文档，不允许含糊）**
  - 只解密**有权抓取**的流量；部署前提与法律边界必须写清
  - **不做主动 MITM**（不重签证书、不改客户端配置）——只做"被动抓包 + 密钥来源"，
    这与本项目"监测/取证"的定位一致
- **G5 decrypted 标记要贯穿全链路**
  - 告警/证据里标注"该命中来自解密流量"，避免取证时把解密内容误当原始证据

## 3. 跑偏判据（发现任一条，立即停手复盘）

1. **连续两个大任务不增加"检测 / 告警 / 处置"能力** ⇒ 偏了
2. **一个任务做完，说不出"用户现在能做什么以前做不到的事"** ⇒ 偏了
3. **前端新增功能没有后端真实数据支撑**（画了一个没数据的界面）⇒ 偏了
4. **文档 / 重构 / 脚手架类任务占比超过三成** ⇒ 偏了
5. **方案里出现"以后要用，所以先做"** ⇒ 按《技术决策方法》重新分类（大概率是"便宜的"，应留到以后）

> 历史教训：大任务 12、13 连续做管理面（启停 / 裁剪 / 清单语义 / 文档对齐），
> 检测能力零增长，用户一句"**感觉越做越偏了**"才发现。**判据 1 就是为这次写的。**

## 5. 明确不做（当前阶段）

- 不做主机日志检测（SIEM / Sigma 类）—— 本项目只做网络流量
- 不接 Suricata 引擎本体（只兼容它的规则格式）
- 不做多机分布式（单机优先，`eventbus` 留演进空间）
- 不做用户体系（延后到可发行版本）
- 不做"为了好看"的前端动效 / 仪表盘
