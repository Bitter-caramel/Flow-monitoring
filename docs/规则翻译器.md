# 规则翻译器（Rule Translator）微型架构

> 版本：v2（讨论定稿：IR 结构 / P0 子集 / 代码落位 / gonids 对拍）
> 日期：2026-10-04
> 状态：设计定稿，尚未实现
> 配套：《定制化与检测规划.md》§4.3（规则格式兼容 Suricata）
> 读者：后续的开发者 / AI agent（本文就是给你看的维护指南）

## 0. 它解决什么问题

把 **Suricata 规则文本**（`.rules`）翻译成**内部可执行格式**，供自研检测引擎匹配流量。

一句话：**规则内容的"事实标准"是 Suricata 格式，我们只做"翻译"，不做"发明"。**

---

## 1. 为什么需要"微型架构"，而不是直接调 gonids

`gonids`（[google/gonids](https://github.com/google/gonids)）能解析/生成 Suricata 规则，但它有**两个致命风险**：

| 风险 | 说明 |
|---|---|
| **维护半死不活** | Google 的仓库常年不更新（社区已有 fork [julienschmidt/gonids](https://github.com/julienschmidt/gonids) 佐证原库不活跃） |
| **语法跟不上** | Suricata 语法持续演进（如 `http.uri; content:"..."` 这类 sticky buffer 是较新的），gonids 未必支持 |

**结论**：不能把生产命脉挂在 gonids 上。要**自己设计一个微型架构**，用自研解析器做生产，gonids 只做对拍验证（见 §6）。

---

## 2. 三层架构（核心）

```
Suricata 规则文本 (.rules)
   │
   ▼
┌─────────────────────────────────────────────┐
│ [1] 解析层 Parser        ← ★ 可替换的一层     │
│     职责：文本 → 语法树 / 原始结构            │
│     实现：自研子集解析器（主力）               │
└─────────────────────────────────────────────┘
   │  原始结构（AST）
   ▼
┌─────────────────────────────────────────────┐
│ [2] 规范化层 Normalizer   ← ★ 稳定接口 = IR   │
│     职责：AST → 内部规则模型 (IR)              │
│     实现：自研（本项目的事实标准）             │
└─────────────────────────────────────────────┘
   │  IR（中间表示）
   ▼
┌─────────────────────────────────────────────┐
│ [3] 编译层 Compiler      ← ★ 面向性能         │
│     职责：IR → 可执行匹配结构 (CompiledRule)  │
│     实现：自研（预编译正则 / 建索引）          │
└─────────────────────────────────────────────┘
   │  CompiledRule
   ▼
检测引擎（internal/modules/detect，热路径进程内）
```

**为什么这样切？** 三层面对的变化速度不同：

| 层 | 变化速度 | 应对 |
|---|---|---|
| 解析层 | **最快**（上游语法演进） | 自研子集、可替换 |
| 规范化层 | 慢（IR 稳定） | 接口层，改动要评审 |
| 编译层 | 中（性能优化会改） | 内部实现，随便优化，只要 `CompiledRule` 语义不变 |

**代码落位**：`internal/modules/rule/`。它是**库（package）**，不是插件进程——编译出的规则要在**热路径进程内**被检测引擎直接消费。

## 3. 中间表示 IR（稳定接口）

**IR = 与 Suricata 语法解耦的内部规则模型**。三层之间的"合同"，全模块最稳定的东西。

具体结构（`ir.go` 里最终定）：

```go
// Rule 一条规则（翻译后的内部表示）
type Rule struct {
    ID          string   // 内部 ID，如 "suricata-2100498"
    Source      string   // "suricata" / "builtin" / "custom"
    SourceID    string   // 原始 sid（保证可回溯到原始规则）
    Name        string   // msg
    Category    string   // 分类树节点（web/pwn/scanner/...）
    Severity    string   // 严重度（由 classtype/priority 映射）
    References  []string // CVE / URL / ATT&CK
    Enabled     bool

    Match  Match
    Action Action
}

// Match 匹配条件
type Match struct {
    Proto            Protocol   // any / tcp / udp / icmp / http / dns / tls / ssh ...
    SrcIP, DstIP     NetSpec    // any / CIDR / 列表 / 取反
    SrcPort, DstPort PortSpec   // any / 单端口 / 范围 / 列表
    Flow             FlowSpec   // to_server / from_client / established / stateless ...
    Conditions       []Condition // 多个条件默认 AND
}

// Condition 单个匹配条件
type Condition struct {
    Kind   ConditionKind // content / pcre
    Buffer Buffer        // payload / http_uri / http_header / http_method /
                         // http_client_body / dns_query / tls_sni ...
    Value  string        // 内容原文 或 正则
    Flags  CondFlags     // nocase / negate / fast_pattern / ...
    Offset, Depth int    // content 的 offset/depth/distance/within
}

// Action 命中动作
type Action struct {
    Kind       string  // 事件类型，如 "sql_injection" / "scanner_probe"
    Severity   string
    Weight     int     // 供态势引擎评分
    Confidence float64
}
```

**IR 设计原则**：

1. **不出现 Suricata 专有名词**（`flowbits`、sticky buffer 原生写法都不进 IR），抽象成"我们引擎能执行"的语义。翻译不过来的，落到 `Unsupported` 列表（见 §7）。
2. **可序列化**（存 DB、可快照、可 diff），便于"规则导入预览"和回归测试。
3. **对引擎友好**（编译层能直接把它变成索引 + 正则）。

## 4. 支持的 Suricata 关键字子集（分期）

| 期 | 关键字 | 说明 |
|---|---|---|
| **P0** | `alert` + 头（proto / src_ip / src_port / dst_ip / dst_port）+ `msg` `sid` `rev` `classtype` `reference` `metadata` | 规则骨架 |
| **P0** | `content` `nocase` `pcre` `depth` `offset` `distance` `within` | 内容匹配（漏扫/Web 特征主力） |
| **P0** | 缓冲前缀 `http_uri` `http_header` `http_method` `http_client_body` `dns_query` `tls_sni` | 定位到具体字段 |
| **P0** | `flow:to_server/from_client/established` | 方向与状态 |
| P1 | `flowbits` `threshold` `detection_filter` `tag` `byte_test` `byte_jump` | 高级特性 |
| 不支持 | 其余（记入 `Unsupported` 清单） | 按需增量 |

> 原则：**先跑通 P0 闭环，P1 与更多关键字按需增量**——缺了再加，代价低。

## 5. 扩展点（维护时就改这几处）

| 要做什么 | 改哪一层 | 具体动作 |
|---|---|---|
| **支持新的 Suricata 语法关键字** | 解析层 + 规范化层 | 1) 解析层识别它；2) 规范化层映射成 IR（或落 `Unsupported`） |
| **接入一种新规则格式** | 加一个 Parser | 写"新格式 → IR"映射，其余两层不动 |
| **加一种匹配类型** | 规范化层 + 编译层 + 引擎 | 1) `Condition.Kind` 加一项；2) 编译层产出 matcher；3) 引擎实现 |
| **换掉/弃用 gonids** | 只动测试 | 删 `gonids_test.go` 即可，生产代码零影响 |

> **红线**：任何扩展都**不许让 IR 出现"某个具体外部库"的痕迹**。

## 6. gonids 的角色：不是"生产解析器"，是"对拍测试参照"

关键认知（2026-10-04 讨论定稿）：**gonids 真正值钱的地方不是"用它解析"，而是它是现成的参照实现。**

- **生产解析**：用**自研子集解析器**（命脉不挂在 gonids 死活上）。
- **验证**：用 gonids 做**对拍测试（differential testing）**——同一份 `.rules` 文件，
  同时喂给「自研解析器」和「gonids」，对比两者的结构化结果；
  **不一致 → 说明自研解析器有 bug**（先怀疑自研：gonids 是社区验证过的）。
- 这就是**免费的测试套件**：不用手写 golden 期望，拿 gonids 当"真理机"。
- 对拍只比较**双方都支持的语法子集**；gonids 不认识、我们也不认识的关键字不参与比较。
- gonids 导入路径 `github.com/google/gonids`（或其 fork `julienschmidt/gonids`），
  **仅用于测试（`_test.go`），不进入生产代码路径**。

## 7. 容错、可测试、可观测

**容错（必须）**：

- **一条规则失败，不影响其它规则**：逐条翻译，失败记错误、跳过，最后汇总。
- **`Unsupported` 清单**：翻译不过来的关键字/语法，收集成清单并计数（而非静默丢弃）。

**可测试（每层独立）**：

| 层 | 测试方式 |
|---|---|
| 解析层 | 给规则文本 → 断言 AST |
| 规范化层 | 给 AST → 断言 IR |
| 编译层 | 给 IR → 断言 `CompiledRule`（正则预编译、索引正确） |
| 端到端 | **golden test**：固定规则集 → 固定 IR 快照（改 IR 会 diff，强制评审） |
| **对拍** | **自研解析 vs gonids**（§6）：同一规则文件，结果不一致即自研有 bug |

**可观测**：

- 翻译统计：总数 / 成功 / 失败 / `Unsupported` 分类计数。
- 导入接口（webUI）展示"哪些规则没被导入、为什么"。

## 8. 包结构

```
internal/modules/rule/           # 规则翻译器（库，非插件进程）
├── doc.go
├── ir.go                # ★ 中间表示（稳定接口，改动需评审）
├── suricata/
│   ├── lex.go           # 词法：一条规则切成「头」+ 选项列表
│   └── parse.go         # 语法：选项解析（content/pcre/缓冲/flow/...）
├── normalize.go         # 规范化层：Suricata AST → IR
├── compile.go           # 编译层：IR → CompiledRule（预编译正则、建端口索引）
├── translate.go         # 对外入口：Translate(text) → ([]CompiledRule, 统计, 错误)
└── gonids_test.go       # 对拍测试：自研解析 vs gonids（仅测试依赖）

internal/modules/detect/         # 检测引擎（消费 CompiledRule）
```

对外只暴露 `translate.go` 入口 + `ir.go` 类型；解析层/编译层是内部实现。

## 10. 维护指南（给未来的开发者 / agent）

1. **改 IR 前先想三遍**：稳定接口，改了影响规范化层、编译层、引擎、快照测试。改 IR 必须同步更新 golden 快照并说明理由。
2. **加功能先问"是哪一层的活"**：语法识别 → 解析层；语义映射 → 规范化层；性能 → 编译层。别越层。
3. **绝不让外部库渗进 IR**：gonids 字段名、Suricata 关键字都不能出现在 IR。
4. **每次改动跑三件事**：单元测试（分层）+ golden 快照（端到端）+ gonids 对拍（验证解析正确性）。
5. **`Unsupported` 不是垃圾桶，是待办清单**：它告诉你们"社区规则里还有哪些语法没支持"。
