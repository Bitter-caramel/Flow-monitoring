# 规则翻译器（Rule Translator）微型架构

> 版本：v1
> 日期：2026-10-04
> 状态：设计，尚未实现
> 配套：《定制化与检测规划.md》§4.3（规则格式兼容 Suricata）
> 读者：后续的开发者 / AI agent（本文就是给你看的维护指南）

## 0. 它解决什么问题

把 **Suricata 规则文本**（`.rules`）翻译成**内部可执行格式**，供自研检测引擎匹配流量。

一句话：**规则内容的"事实标准"是 Suricata 格式，我们只做"翻译"，不做"发明"。**

---

## 1. 为什么需要"微型架构"，而不是直接调 gonids

`gonids`（[google/gonids](https://github.com/google/gonids)）能解析/生成 Suricata 规则，但它有**两个致命风险**：

| 风险 | 说明 |
|---|---|
| **维护半死不活** | Google 的仓库常年不更新（社区已有 fork [julienschmidt/gonids](https://github.com/julienschmidt/gonids) 佐证原库不活跃） |
| **语法跟不上** | Suricata 语法持续演进（如 `http.uri; content:"..."` 这类 sticky buffer 是较新的），gonids 未必支持 |

**结论**：不能把项目命脉挂在 gonids 上。要**自己设计一个微型架构**，把 gonids 降级为"一个可替换的零件"。

---

## 2. 三层架构（核心）

```
Suricata 规则文本 (.rules)
   │
   ▼
┌─────────────────────────────────────────────┐
│ [1] 解析层 Parser        ← ★ 可替换的一层     │
│     职责：文本 → 语法树 / 原始结构            │
│     实现：gonids（可选） / 自研子集解析器      │
└─────────────────────────────────────────────┘
   │  原始结构
   ▼
┌─────────────────────────────────────────────┐
│ [2] 规范化层 Normalizer   ← ★ 稳定接口 = IR   │
│     职责：原始结构 → 内部规则模型 (IR)         │
│     实现：自研（本项目的事实标准）             │
└─────────────────────────────────────────────┘
   │  IR（中间表示）
   ▼
┌─────────────────────────────────────────────┐
│ [3] 编译层 Compiler      ← ★ 面向性能         │
│     职责：IR → 可执行匹配结构 (CompiledRule)  │
│     实现：自研（预编译正则 / 建索引）          │
└─────────────────────────────────────────────┘
   │  CompiledRule
   ▼
检测引擎（internal/modules/detect）
```

**为什么这样切？** 因为三层面对的变化速度不同：

| 层 | 变化速度 | 应对 |
|---|---|---|
| 解析层 | **最快**（外部库 + 上游语法演进） | 设计成**可替换**，换掉不影响其它层 |
| 规范化层 | 慢（我们的 IR 稳定） | 是**接口层**，改动要慎重、要评审 |
| 编译层 | 中（性能优化会改） | 内部实现，随便优化，只要产出的 `CompiledRule` 语义不变 |

---

## 3. 中间表示 IR（稳定接口）

**IR = 与 Suricata 语法解耦的内部规则模型**。它是三层之间的"合同"，也是整个模块最稳定的东西。

概念结构（实现时细化）：

```
Rule
├── 元信息: ID / Name / Category / Severity / Description / References / Enabled
├── Match:  条件组合 (Logic: and|or) + []Condition
└── Action: 命中后的事件 (kind / weight / confidence)

Condition
├── Type:  "port" | "proto" | "content" | "regex" | "http_uri" | "flow_rate" | ...
├── Field: 匹配哪个字段
└── 参数:  values / regex / ports / thresholds ...
```

**IR 的设计原则**：

1. **不出现 Suricata 专有名词**（如 `flowbits`、sticky buffer 的原生写法），要抽象成"我们引擎能执行"的语义。翻译不过来的，落到 `Unsupported` 列表（见 §6）。
2. **可序列化**（存 DB、可快照、可 diff），便于"规则导入预览"和回归测试。
3. **对引擎友好**（编译层能直接把它变成索引 + 正则）。

---

## 4. 扩展点（维护时就改这几处）

| 要做什么 | 改哪一层 | 具体动作 |
|---|---|---|
| **支持新的 Suricata 语法关键字** | 解析层 + 规范化层 | 1) 解析层能识别它；2) 规范化层把它映射成 IR（或落入 `Unsupported`） |
| **接入一种新规则格式**（如未来某个新格式） | 加一个 Parser | 写"新格式 → IR"的映射，其余两层不动 |
| **加一种匹配类型**（如 `dns_query`） | 规范化层 + 编译层 + 引擎 | 1) IR 的 `Condition.Type` 加一项；2) 编译层产出对应 matcher；3) 引擎实现该 matcher |
| **换掉 gonids** | 只改解析层 | 写新的 Parser 实现，规范化层/编译层不动 |

> **红线**：任何扩展都**不许让 IR 出现"某个具体外部库"的痕迹**。IR 一旦被 gonids 绑架，换库就变成大手术。

---

## 5. gonids 的角色与"先测后定"策略

- gonids **只是解析层的一种实现**，不是架构的一部分。
- **落地方式（与"先测"结合）**：
  1. **先测**：拿一个真实规则集（如 ET Open 的 `.rules`）喂给 gonids，统计**解析成功率**和**报错关键字分布**。
  2. **判断**：
     - 覆盖率够 → gonids 作为解析层实现，我们在它之上做规范化。
     - 覆盖率不够 → 自研**子集解析器**（只解析"我们引擎能执行的规则子集"，把不支持的显式列出来）。
  3. **无论哪种**，解析层都通过统一接口暴露，随时可换。

---

## 6. 容错、可测试、可观测

**容错（必须）**：

- **一条规则失败，不影响其它规则**：逐条翻译，失败记错误、跳过，最后汇总。
- **`Unsupported` 清单**：翻译不过来的关键字/语法，收集成清单并计数，便于后续按需扩展（而不是静默丢弃）。

**可测试（每层独立）**：

| 层 | 测试方式 |
|---|---|
| 解析层 | 给规则文本 → 断言解析出的原始结构 |
| 规范化层 | 给原始结构 → 断言 IR |
| 编译层 | 给 IR → 断言 `CompiledRule`（正则是否预编译、索引是否正确） |
| 端到端 | **golden test**：固定规则集 → 固定 IR 快照（改动 IR 时快照会 diff，强制评审） |

**可观测**：

- 翻译统计：总数 / 成功 / 失败 / `Unsupported` 分类计数。
- 导入接口（webUI）展示"哪些规则没被导入、为什么"。

## 7. 包结构（建议）

```
internal/modules/rules/          # 规则翻译器
├── doc.go
├── ir.go                # ★ 中间表示（稳定接口，改动需评审）
├── parser/              # 解析层（可替换）
│   ├── parser.go        # Parser 接口
│   ├── gonids_parser.go # gonids 实现（可选）
│   └── native_parser.go # 自研子集解析器（备选/主力）
├── normalize.go         # 规范化层：原始结构 → IR
├── compile.go           # 编译层：IR → CompiledRule
└── translate.go         # 对外入口：Translate(text) → (结果, 统计, 错误)

internal/modules/detect/         # 检测引擎（消费 CompiledRule）
```

对外只暴露 `translate.go` 的入口 + `ir.go` 的类型；解析层/编译层都是内部实现。

---

## 8. 维护指南（给未来的开发者 / agent）

1. **改 IR 前先想三遍**：它是稳定接口，改了会影响规范化层、编译层、引擎、以及快照测试。改 IR 必须同步更新 golden 快照并说明理由。
2. **加功能先问"是哪一层的活"**：语法识别 → 解析层；语义映射 → 规范化层；性能 → 编译层。别越层。
3. **绝不让外部库渗进 IR**：gonids 的字段名、Suricata 的关键字，都不能出现在 IR 里。
4. **每次改动跑三件事**：单元测试（分层）+ golden 快照（端到端）+ 真实规则集覆盖率统计（回归）。
5. **`Unsupported` 不是垃圾桶，是待办清单**：它告诉你们"社区规则里有哪些语法我们还没支持"，按需扩展。
