## 0. 一句话

> **模块进程订阅事件只有 `plugin.Host.Poll(topic, since, max)` 一条路。**
> `pollsource` 把这条"拉取接口"包装成 channel，业务消费者只管从 channel 读；
> `alert` 用这个样板跑在独立插件进程里，落盘为 JSONL。

数据流：

```
Host.Poll(detect.feature) → pollsource.Source.C() → 解码/业务处理 → alert.Consumer → FileSink(JSONL)
```

## 1. 三步写一个新消费者

### 第 1 步：用 `pollsource` 把总线拉成 channel

```go
src := pollsource.New(host, "detect.feature", pollsource.Options{
    Batch:      100,              // 每轮最多拉多少（默认 100）
    Idle:       200 * time.Millisecond, // 空闲轮询间隔（默认 200ms）
    FromLatest: false,            // true = 启动时跳过历史，只消费新事件
})
defer src.Close()                 // ★ 关闭后 channel 会被关闭，消费者自然收尾
```

- `src.C()` 可以直接交给一个从 channel 消费的消费者；
- `src.Stats()` 返回 `Delivered / Gaps / Errors / LastSeq`，用于健康上报；
- **投递满时阻塞等待（背压），绝不丢弃**。

### 第 2 步：实现业务逻辑（可复用 `alert.Consumer` 的形态）

消费者只依赖 channel 和落点接口，不感知宿主/进程：

```go
type Sink interface {
    Write(ev Event) error
    Flush() error
    Close() error
}

cons := NewConsumer(src.C(), sink, ConsumerOptions{})
```

- `alert.Consumer` 已内置**去重窗口**与 `Written()/Suppressed()` 计数；
- 若新模块需要"再发事件"，在消费循环里调用 `host.Publish(topic, jsonBytes)` 即可；
- 业务逻辑不要直接碰 `plugin.Host.Poll`，否则每个模块都会重复实现游标/断层/背压。

### 第 3 步：在 `Module()` 里起 goroutine + `OnHealth` 报进度

```go
func Module() *plugin.Runtime {
    m := &alertModule{}
    return &plugin.Runtime{
        Spec: plugin.Manifest{
            ID:       "modules.alert",
            Layer:    plugin.LayerFeature,
            Provides: []string{"alert.sink"}, // 无 HTTPBase
        },
        OnStart:  m.start,   // 建 sink/source/consumer，起 goroutine 后立即返回
        OnStop:   m.stop,    // 取消 ctx → 关 source → 关 consumer（幂等）
        OnHealth: m.health,  // 已投递/断层/错误/已写/已抑制
    }
}
```

`OnStart` 里**不要**把消费循环直接跑在调用线程上，否则 `Runtime.Start()` 永远不返回。
`alert` 的实际实现见 `internal/modules/alert/module.go`。

## 2. 四条必须遵守

| # | 规则 | 为什么 |
|---|---|---|
| 1 | **断层要计数** | 宿主是内存 ring，`since` 过旧时返回的第一条会跳号。允许继续消费，但必须 `Gaps++` 并写 `warn` 日志，否则"漏了一段没人知道"。判据：`len(evs) > 0 && evs[0].Seq > since+1`。 |
| 2 | **不要丢事件（背压不丢弃）** | 投递 channel 满时阻塞等待。丢事件 = 下游漏告警/漏处置，比"慢"更糟。 |
| 3 | **`OnStart` 不许阻塞** | 宿主按顺序启动模块，一个消费者卡住会拖死整条启动链。业务失败用 `OnHealth` 如实上报，而不是让 `Start` 返回错误卡住。 |
| 4 | **`OnStop` 必须幂等** | 宿主可能重复调用/兜底回收。用 `sync.Once` 包住关停；顺序必须是**先关 source（排空 channel）再关 consumer（冲刷 sink）**，否则最后几条会漏。 |

## 3. `pollsource` 的行为约定

| 行为 | 实现 |
|---|---|
| 增量拉取 | `Poll(topic, since, Batch)` → 逐条投递 → `since = 最后一条.Seq` |
| 无事件 | `time.Sleep(Idle)`（可被 `Close` 立即打断） |
| 断层检测 | 每批第一条 `Seq > since+1` ⇒ `Gaps++` + `host.Log("warn", ...)`，继续消费 |
| `FromLatest` | 构造时同步 `Poll(topic, 0, 1<<20)` 取最后一条 `Seq` 作为起点；拿不到从 0 开始。只取最后一条，不按 `max` 预分配 |
| 载荷转换 | `eventbus.Event{Topic, Payload: rec.Data, TraceID, Time}` |
| 关闭 | `Close()` 后循环退出、channel 关闭；关闭后的 channel 仍会把缓冲读完 |
| 背压 | 带 256 缓冲；满时阻塞发送（`Close` 时优先退出） |

## 4. 范例：`alert` 消费者做了什么

1. 解析 `ConfigSnapshot.Raw` 里的 `alert.sink_path`（默认 `data/alerts.jsonl`）；
2. `pollsource.New(host, "detect.feature", opts)` 拉取检测特征；
3. 把扁平 `detect.feature` JSON 解码成 `alert.Event`（兼容已是 `alert.Event` 的载荷）；
4. 交给 `alert.NewConsumer` 做去重/抑制，再用 `FileSink` 追加写 JSONL；
5. `OnHealth` 报 `已投递 N / 断层 G / 错误 E / 已写 W / 已抑制 S`。

完整实现：`internal/modules/alert/module.go`。
