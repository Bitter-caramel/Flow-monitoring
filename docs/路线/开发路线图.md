## 0. 产品定义

> **一套能"实时监测 + 事后分析"网络攻击流量的平台（IDS/IPS 方向）。**

两个能力，缺一不可：

| 能力 | 时间观 | 用户问题 | 交付形态 |
|---|---|---|---|
| **动态监测** | **现在** | "现在有人在打我吗？" | 常驻运行，实时告警，最终有**总控大屏** |
| **静态分析** | **过去** | "这份抓包里到底发生了什么？" | 上传/选定文件，一次性分析，可反复回看 |

**三条硬指标**（判断一切任务该不该做）：

1. **能看见攻击** —— 有流量进来时，产出可解释的告警（规则 ID / 命中位置 / 证据）
2. **能持续看见** —— 不需要手动跑命令行，服务常驻、告警持续产出、界面能看到
3. **能应对** —— 从告警 → 评价 → 处置 → 串链，形成闭环

## 1. 现状盘点（2026-10-21 核实）

### 1.1 已经能跑的（可复用）

| 层 | 已有 | 状态 |
|---|---|---|
| 内核 | registry 拓扑排序 / pluginhost 进程管理 / transport 网关+WS / eventbus / storage / 模块控制面 | ✅ |
| 解析 | pcapng reader+writer、gopacket 解码、L7 解析（HTTP/DNS/TLS/DHCP）、归流、TCP 重组 | ✅ 库 |
| 检测 | 规则翻译器（Suricata→IR→CompiledRule）、检测引擎（Ctx/提取器/匹配语义）、告警 | ✅ 库 |
| 采集 | `capture` 进程：Source 接口 + 回放数据源 + 热路径 + 发事件 + 健康上报 + panic 隔离 | ✅ 进程 |
| 告警链 | `detect.feature` 事件 → 宿主 `alerting`（环形缓冲）→ `/api/alerts` → WS → 前端面板 | ✅ |
| 静态入口 | `importer`（上传入库）、`query`（分页查包）、证据留存 `collect`（库） | ✅ 进程/库 |
| 规则来源 | 四号段 + 按目录判来源 + sid 校验 + 按来源导出 | ✅ 库 |
| 前端 | 3 工作台骨架、4 个面板、URL 即状态、三态模块显示、错误边界 | ✅ |

### 1.2 缺的（按严重度）

| # | 缺什么 | 影响 | 状态 |
|---|---|---|---|
| 1 | **静态检测**（对指定文件跑一次分析并产出告警）| 静态工作台是空壳 | ❌ |
| 2 | **Run（分析任务）概念**：谁在跑、跑到哪、告警归属 | 告警无法区分静态/动态 | ❌ |
| 3 | **静态告警的持久化**（动态是流水，静态要能反复回看）| 静态结果看完就没了 | ❌ |
| 4 | **事件消费者样板**（订阅 → 处理 → 再发事件）| 阻塞 situation/alert/disposal/attackchain 4 个核心模块 | ❌ |
| 5 | **模块健康/运行状态上报**（capture 跑了多少包，宿主看不见）| 排障困难 | ❌ |
| 6 | **8 个模块仍是空目录**：situation / alert / attackchain / disposal / auth / case / export / ioc | 蓝队闭环没有 | ⬜ |
| 7 | 真实网卡采集（现在只有回放）| 不能真·实时 | ❌ |
| 8 | TLS 解密（方向 G）| HTTPS 只能看 SNI | ❌ |
| 9 | 用户体系（已延后）| 不能多用户 | ⏸ |
| 10 | 打包/安装/合规 | 不能交付 | ❌ |

> ★ 好消息：`alert`(7 文件)、`collect`(7 文件) 等**已经有库代码**，做成进程的工作量远小于从零写。

## 2. 静态 vs 动态：哪些复用、哪些必须分开

### 2.1 后端：**高度重合，一套实现**（只换数据源）

| 能力 | 动态 | 静态 | 结论 |
|---|---|---|---|
| 数据源 | 网卡 / 回放 | 指定 pcapng 文件 | **`Source` 接口**（已做）✅ |
| 解码 | 同 | 同 | `decoder` ✅ 复用 |
| 归流 + 重组 | 同 | 同 | `hotpath` ✅ 复用，但**每个 run 独立实例**（状态不能共享）|
| 规则 / 检测引擎 | 同 | 同 | **共享只读** ✅ |
| 告警产出 | `detect.feature` | 同，带 `mode=static` | 同一条事件线 ✅ |
| 告警存储 | 内存环形（流水，丢了也无所谓）| **必须持久化**（可反复回看）| ★ **要加**（唯一实质差异）|
| 任务/会话 | 监听会话 | 分析任务 | **统一成 `Run`**（`mode` 区分）|
| 证据留存 | pcapng 段（`collect`）| 读同一批文件 | 复用 ✅ |

**结论：后端只有"静态告警要持久化"这一个实质差异**，其余全部复用。

### 2.2 前端：**表现差异巨大，页面必须分开**

| 关注点 | 动态工作台 | 静态工作台 | 组件策略 |
|---|---|---|---|
| 数据源选择 | 选网卡/回放 + **开始/停止** | **上传/选择文件** + 开始分析 | **分开**（语义完全不同）|
| 主视图 | **总控大屏**（数字/趋势/滚动流）| **任务列表 → 单文件详情**（表格/分页/下钻）| **分开** |
| 时间观 | 从现在往前（滚动窗口）| 文件起止时间（可选范围过滤）| 分开 |
| 告警展示 | 实时流：WS 推送、去重、聚合 | 命中列表：可全量、可排序、可跳包 | ★ **共用表格组件**，行为不同 |
| 包列表 | 最近 N 条（环形）| 全量分页 + 搜索 | ★ **共用表格组件**，数据源不同 |
| 筛选器 | 少（时间窗/严重度）| 多（IP/端口/协议/规则/时间段）| ★ **共用组件**，配置不同 |
| 详情 | 抽屉/侧栏 | 抽屉/侧栏 | ★ **共享** |
| 操作 | 处置（封禁）、标记 | 导出、生成报告 | **分开** |
| 刷新方式 | WS 推送 + 兜底轮询 | 按需请求（分页/搜索）| 分开 |
| 空态文案 | "监听中，暂无告警" | "该文件未命中规则" | 分开 |

**结论：前端"页面编排"必须分开（两套工作台），但"原子组件"必须共享（表格/筛选/详情/时间）。**

⇒ **不是"写两遍"，是"一套组件 + 两套编排"。**

## 3. 地基清单（铺模块之前必须先补）

| # | 地基项 | 为什么阻塞 | 依赖 |
|---|---|---|---|
| 1 | **事件消费者样板** | situation/alert/disposal/attackchain 都是"订阅→处理→再发事件"，无样板则各写各的 | 无 |
| 2 | **Run 概念 + 静态告警持久化** | 没有它，"静态结果"看完就没了；告警也无法按模式区分 | 16-3 |
| 3 | **模块健康/状态上报**（包数、进度、错误）| 长跑的 capture 出问题，宿主完全看不见 | 无 |
| 4 | **配置分发标准化**（模块读自己那段配置）| 现在每个模块手解 `ConfigSnapshot.Raw`，容易各写各的 | 无 |
| 5 | **假 Host 测试桩抽公共包** | 每个新模块都要重写一遍测试桩 | 无 |
| 6 | **前端共享组件库**（表格/筛选/详情/时间格式化）| 两个工作台都要用，先抽再铺 | 16-2 |
| 7 | **证据留存接续**（collect 的证据包 → 静态分析入口）| "边上边存、下机再研"这条线的接点 | 无 |
| 8 | **面板可见性感知后端能力** | 现在面板用 `workbenches` **静态声明**，只能靠人记得改；一忘就会出现"永远为空的面板"（16-2 就发生过两次：静态挂实时告警、动态挂查静态文件的包列表）。应改为后端上报能力、前端据此决定入口显隐 | 16-2 |

> ★ 判据（来自 16-2 的实际教训）：**面板可见性必须等于真实能力**。
> 加面板之前先问："点进去，里面真的有数据吗？"——没有就先别加。

## 5. 明确不做（当前阶段）

- 不做主机日志检测（SIEM / Sigma 类）—— 只做网络流量
- 不接 Suricata 引擎本体（只兼容规则格式）
- 不做多机分布式（单机优先）
- 不做"为了好看"的动效/仪表盘
- 不做主动 MITM（TLS 解密只做被动 + 密钥来源）
