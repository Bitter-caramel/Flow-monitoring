# 检测引擎（Detection Engine）设计

> 版本：v1
> 日期：2026-10-08
> 状态：设计定稿，待实现（本文是 9-2 ~ 9-6 所有编码任务的依据）
> 配套：《规则翻译器.md》（IR 与规则侧编译）、《规则翻译器扩展指南.md》（怎么加关键字）、《定制化与检测规划.md》§5（事件线）
> 读者：后续开发者 / AI agent

---

## 0. 一句话

> **检测引擎 = 把「规则（`CompiledRule`）」和「流量（包 + 流）」接起来，产出「告警（`Alert`）」。**

它**只认 `CompiledRule`**——不认识 Suricata 规则文本（那是上一环 `pipeline.Translate` 的事）。

---

## 1. 它在系统里的位置

```
监听/回放 → 解析(decoder+L7) → 聚合(analyzer) → ★检测(detect) → 告警
                                                    │
                                    （冷路径：告警 → 事件总线 → 态势/处置/攻击链）
```

> ★ **接入现状（2026-10-17）**：引擎与 `internal/hotpath` 编排均已实现，但目前只被 `cmd/parse-cli` 调用（离线回放）；宿主进程（`cmd/server`）尚未接热路径。

- **检测在热路径上**（每包都跑），所以它对性能的要求是**零容忍**（见 §8）；
- 告警出去之后的链路（事件总线、态势、处置、攻击链）**不在本引擎内**，属于冷路径，后续另做；
- **依赖方向严格单向**：`detect → rule`、`detect → datamodel`；**`rule` 绝不认识 `detect`**。

---

## 2. 两次编译（本设计的关键分层）

```
规则文本 ──(rule/pipeline.Translate)──▶ CompiledRule    ← 【规则侧编译】与数据源无关
CompiledRule ──(detect.Compile)──────▶ Program          ← 【数据源侧绑定】缓冲名 → 函数指针
```

**为什么必须分两次**：

1. `rule` 包不能依赖 `detect`（否则循环依赖，破坏单向结构）；
2. **"有哪些缓冲区、每个怎么取"是数据源的知识，不是规则的知识**。
   规则只说"在 `http_uri` 里找这个串"，"`http_uri` 从哪来"是引擎的事。

**好消息**：`rule.Compile` 已经做完了重活（`nocase` 的小写预置 `Lower`、`pcre` 的正则预编译 `Regex`、
`content` 的取反标志），所以 `detect.Compile` **只需要绑定缓冲区**（把 `Buffer` 名字换成函数指针）。

## 3. 检测输入单元：`Ctx`

```go
// Ctx 一次检测的输入单元。
// 今天只有"包 + 它所属的流"；将来上 TCP 重组，只是这里多一个字段 —— 引擎其余部分不动。
type Ctx struct {
    Pkt  *datamodel.Packet // 已完成解码 + L7 解析（含 §4 需要的字节边界数字）
    Flow *datamodel.Flow   // 它属于哪条流（带 TCP 状态）—— flow: 筛选用它
    // P1: Stream *reassembly.Stream
}
```

**设计约束**：

- **必须是结构体，不能是接口**：热路径要零动态派发；将来加流只是加字段；
- 调用方（parse-cli / 未来的实时监听）**必须保证** `Pkt` 已完成解码与 L7 解析，`Flow` 已归属；
- `Ctx` 是**只读**的：检测**绝不修改** `Pkt` / `Flow`。

## 4. 缓冲区与提取器（本设计最需要定死的地方）

规则的一个条件 = `(缓冲名, 模式)`。缓冲名说"去哪段字节里找"，**提取器**负责把那段字节取出来。

```go
// Extractor 缓冲区提取器：给定检测单元，返回该缓冲区的字节。
// ★ 返回 nil 表示"该缓冲区在当前单元里不存在"，**不等于**空缓冲区。
type Extractor func(*Ctx) []byte

// 引擎自己的注册表：缓冲名 → 提取器。只在启动期写，之后只读（无需加锁）。
var extractors = map[rule.Buffer]Extractor{ ... }
```

### 4.1 三条铁律

1. **`nil` 表示"不存在"，不是"空"**。
   非 HTTP 的包里 `http_uri` **不存在**；而 `GET / HTTP/1.1` 里 `http_uri` 是 `/`（**存在且很短**）。
   这两件事在取反语义下会导向不同结果（见 §5.4），**不能混为一谈**。

2. **能取"线上原始字节"就取原始字节**；协议本身没有连续字节表示的，才取**规范化值**。
   - HTTP 类：线上就是一段连续字节 → **零拷贝切片**，语义忠实；
   - DNS `dns_query`：线上是**长度前缀标签 + 压缩指针**，根本不存在"一段连续的 `evil.example`"
     → 只能返回**规范化后的点分名**（Suricata 同样如此）。**这不是将就，是正确。**

3. **绝不返回"拼凑出来的近似值"**。
   （反例：拿 `Host`+`User-Agent` 拼一个假 `http_header`。）宁可返回 `nil` 并在导入报告里暴露"不支持"，
   也不要让规则行为不可预测。

### 4.2 P0 缓冲清单

> 偏移一律**相对本包应用层载荷**（即相对 `pkt.Data[pkt.PayloadOff]`），由 L7 层记录、检测层现切。
> **L7 层只记数字、不存 `[]byte`**：避免结构绑定抓包缓冲区的生命周期（实时抓包缓冲区会被复用）。

| 缓冲 | 取法（`P = pkt`，`po = P.PayloadOff`） | 何时为 `nil`（不存在） |
|---|---|---|
| `payload` | `P.Data[po : po+P.PayloadLen]` | `P.PayloadLen <= 0` |
| `http_header` | `P.Data[po : po+P.HTTP.HeaderLen]` | `P.HTTP == nil` 或 `HeaderLen == 0` |
| `http_client_body` | `P.Data[po+P.HTTP.BodyOff : po+P.PayloadLen]` | `P.HTTP == nil` 或 `BodyOff == 0` 或 `BodyOff >= PayloadLen`（无正文） |
| `http_uri` | `P.Data[po+P.HTTP.URIOff : po+P.HTTP.URIOff+P.HTTP.URILen]` | `P.HTTP == nil` 或 `URILen == 0` |
| `http_method` | 同上，用 `MethodOff/MethodLen` | `P.HTTP == nil` 或 `MethodLen == 0` |
| `dns_query` | `[]byte(P.DNS.Questions[0].Name)`（规范化点分名，**会分配**） | `P.DNS == nil` 或 `len(Questions) == 0` |
| `tls_sni` | `[]byte(P.TLS.SNI)`（SNI 原文，**会分配**） | `P.TLS == nil` 或 `SNI == ""` |

**P1 待补**（本轮不做）：`http_stat_*`、`file_data`、`dns_query` 的响应侧、`tls_cert_*`、`ja3_hash` 等。

### 4.3 未注册的缓冲怎么办

`detect.Compile` 时若某条件引用了**未注册**的缓冲 → **该规则标记为不支持并剔除**，
计入**导入报告**（"你的规则里用到我们还不支持的缓冲区 X"）。
**绝不能悄悄让它永远匹配不上** —— 那等于静默失效。

## 5. 匹配语义（逐条对齐 Suricata）

一条规则 = 一组条件，**按在规则里出现的顺序求值**。

### 5.1 总原则

> **一条规则命中 ⟺ 它的所有条件都成功。** 任一条件失败 → 整条规则不匹配（不再继续求值）。

### 5.2 `content`

在该条件的**缓冲**里搜索 `Value`；`nocase` 时大小写不敏感（用预置的 `Lower`）。

- **`offset` / `depth` 相对于"上一次匹配的结束位置"**（第一条 `content` 相对于缓冲起点）：
  - `offset: n` → 从「上次结束 + n」开始找；
  - `depth: d` → 只在「起点 + d」个字节以内找；
  - 两者可同时存在。
- **找不到 → 该条件失败**；
- **`negate`（`content:!"x"`）**：**找不到才算成功**。

### 5.3 `pcre`

用预编译的 `Regex` 在缓冲里找（`Regexp.FindIndex`），找到即成功；`negate` 时反过来。
`offset`/`depth` 语义同 §5.2。

### 5.4 缓冲不存在（`nil`）时的语义 ★ 必须现在定死

| 条件 | 缓冲不存在时 |
|---|---|
| **非取反**条件 | **失败**（该条件不成立） |
| **取反**条件 | ★ **整条规则不匹配**（而不是"取反成功"） |

**为什么取反也判为不匹配**：用了 `http_uri` 就说明这条规则是**给 HTTP 流量写的**；
非 HTTP 流量不该因为"取反"而命中（那会变成**误报**）。
P0 取这个**保守**语义；将来与 Suricata 对拍时确认它的实际行为再对齐。

### 5.5 `flow:` 筛选（规则级，不是条件）

用 `Ctx.Flow` 的 TCP 状态（analyzer 的状态机）判定：

| `flow` 值 | 判定 |
|---|---|
| `stateless` | 不筛（永远通过） |
| `established` | 流状态 ∈ {`FlowEstablished`, `FlowHalfClose`, `FlowClosed`}（即**已完成握手**） |
| `to_server` / `from_client` | ★ **P0 不筛**（见下） |
| 空 | 不筛 |

**为什么 P0 不做方向筛选**：`Pkt.StreamDir` 只知道"`0` = A→B / `1` = B→A"，
而 **A/B 是按 IP 大小规范化的，跟"哪一侧是服务端"没关系**；`Flow` 里也没有"服务端"标记。
**不知道方向就不该猜** —— 猜错会把"请求规则"套到响应上，直接制造误报。

P0 的做法：**放过**（不筛方向），但在**导入报告**里如实标注
"该规则的 `flow` 方向条件未生效"（记进 `Program.Unsupported`）。
**P1** 需要 analyzer 先补一个"服务端方向"的语义（例如记录发起 SYN 的方向），再实现方向筛选。

### 5.6 规则头筛选（协议 / 端口 / IP）

| 维度 | P0 怎么办 |
|---|---|
| 协议 | ✅ **按「协议集合」判定**（见下） |
| 源端口 / 目的端口 | ✅ **必须分开判**：用 `Match.SrcPort` 判 `Pkt.SrcPort`、`Match.DstPort` 判 `Pkt.DstPort`。★ **不要用 `CompiledRule` 里合并过的 `AnyPort`/`Ports`/`PortRanges`** —— 它丢失了源/目的区分，会**误报**（`any 1024:65535 -> any 80` 会放进"源 50000 / 目的 9999"的包）。合并视图只留给导入报告/展示 |
| **IP** | ❌ **P0 不做** —— IR 里 `$HOME_NET` / `$EXTERNAL_NET` 是**原样保留的变量名**，还没有变量表。**P1 补"IP 变量表"** |

#### 协议：一个包属于「一组协议」，不是一个协议 ★

规则里写 `tcp`，包是 `HTTP over TCP` —— **必须命中**。所以判据是"**这个包属不属于该协议**"，
而不是"这个包的协议等于什么"。

协议集合由 `datamodel.FillProtocols(p, dst)` 给出（**零分配**、去重），判定规则：

| 包的字段 | 归入协议 |
|---|---|
| `IPProto == 6` | `tcp` |
| `IPProto == 17` | `udp` |
| `IPProto == 1 / 58` | `icmp` |
| `HTTP != nil` | `http` |
| `DNS != nil` | `dns` |
| `TLS != nil` | `tls` |
| `Proto == "SSH"` | `ssh`（SSH 无独立结构体，只能用展示名，P1 再补） |

> ★ **为什么不能拿 `Pkt.Proto` 当索引用**：它是**展示名**（`"HTTP"` / `"TLSv1.2"` / `"TCP"`），
> 而且 **HTTP 解析成功会把 `"TCP"` 覆盖成 `"HTTP"`** —— 用它查表会**永远查不到**，
> 导致"所有限定协议的规则被静默跳过"（踩坑 15 就是这个）。
> 名字与 `rule.Protocol` 的取值一一对应；`detect` 有一条一致性测试防止两边词表漂移。

> **P1（不阻塞引擎）**：把 L7 那段补进 `datamodel.Packet.PathStr`，让"协议路径"成为完整可对外用的表示
> （届时可直接支撑"查所有 http 流量"、资产画像、前端按协议过滤；DB 侧建议用 `text[]` + GIN 索引，
> 而不是对字符串做正则）。当前实测 `PathStr` 只到 L4（如 `,eth,ip4,tcp,`）。

## 6. 编译产物：`Program`

```go
// Program 一条"可直接执行"的规则：缓冲名已经换成函数指针。
type RuleProgram struct {
    ID       string            // 规则 ID（suricata-<sid>）
    Name     string            // msg
    Severity string
    Action   rule.Action
    Proto    rule.Protocol
    AnyPort  bool
    Ports    []uint16
    Ranges   []rule.PortRange
    Flow     rule.FlowSpec
    Conds    []Cond            // ★ 按顺序求值
    // 导入期信息（热路径不读）
    Unsupported []string
}

// Cond 一个已绑定的条件。
type Cond struct {
    Kind    rule.ConditionKind // content / pcre
    Extract Extractor          // ★ 编译期固化：热路径直接调用，零 map 查找、零接口派发
    Buf     rule.Buffer        // 仅用于告警里报"命中在哪个缓冲"
    Content []byte             // content：模式原文
    Lower   []byte             // content+nocase：已预转小写
    Regex   *regexp.Regexp     // pcre
    Negate  bool
    Offset  int
    Depth   int
}
```

> **热路径的形态**：遍历 `Conds` → 调 `c.Extract(ctx)` → 在返回的切片上做 `bytes.Index` / `Regex.FindIndex`。
> **没有任何 map 查找、没有接口方法派发、没有反射。**

## 7. 规则集与导入报告

```go
type RuleSet struct {
    Rules []RuleProgram
    // 粗筛索引（每包查一次，不是每条件查一次 —— 这不违反 §8 的红线）
    byProto   map[rule.Protocol][]int
    byDstPort map[uint16][]int
    anyDst    []int
}

func Load(path string) (*RuleSet, *ImportReport)
```

**`ImportReport`（几乎白送，`TranslateResult` 里都有）**：

- 总条数 / 成功载入 / 解析失败（含**行号**与原因）
- **不支持项汇总**（`Unsupported map[string]int`：未知关键字、被丢弃的条件）
- **因"缓冲不支持"被剔除的规则**（§4.3）
- 备注：`Unsupported` 为空的规则才算"全功能支持"

## 8. 性能红线（与《扩展指南》§5 一致）

> **翻译/编译都不在热路径上；热路径是"每包跑一次"的那条。**

| 位置 | 要求 | 做法 |
|---|---|---|
| 绑定缓冲（`detect.Compile`） | 不关键 | 每条规则编译时查一次 map |
| **每包匹配（`Engine.Match`）** | **零容忍** | 条件里存的是**函数指针**；缓冲字节用**切片现切**（零拷贝）；`pcre` 的正则在**编译期**预编译；`nocase` 的**模式**小写在编译期预置 |
| **`nocase` 的匹配** | **零分配** | ★ 被匹配的字节是**运行期**才拿到的，**不能**用 `bytes.ToLower`（每次分配）。用自写的 **ASCII 大小写不敏感搜索**在匹配时就地折叠比较 |
| 规则索引 | 每包查一次 | `byProto` / `byDstPort` 粗筛，把候选规则数压下来 |
| 注册表并发 | 安全 | 启动期写、之后只读 → 无需加锁 |
| **不许改输入** | —— | 引擎**只读** `Ctx`，绝不修改 `Pkt`/`Flow` |
| 分配 | 尽量零 | 切片现切不分配；`dns_query`/`tls_sni` 因协议所限会有一次分配（可接受，P1 再优化） |

## 9. 告警：`Alert`

```go
type Alert struct {
    RuleID   string
    Name     string    // msg
    Severity string
    Weight   int
    Time     time.Time
    SrcIP    string; SrcPort uint16
    DstIP    string; DstPort uint16
    Proto    string
    StreamID int       // 流 ID（-1 = 未归属）
    Buffer   rule.Buffer // 命中在哪个缓冲区
    Offset   int         // 命中位置（相对该缓冲区）
    Snippet  string      // 命中的一小段上下文（便于人工核对，截断到合理长度）
}
```

P0 里 `Alert` **只在进程内返回**（由 parse-cli 打印）。**接事件总线 `alert.lifecycle` 是后续任务**（冷路径）。

## 10. 集成点：`parse-cli --detect <规则文件>`

逐包：解码 → L7 → 归属流 → 检测 → 收集告警，跑完统一打印：
**告警列表（按规则 ID 聚合计数）+ 命中明细 + 导入报告**。
不带 `--detect` 时**行为完全不变**。

---

## 11. P0 明确不做（边界，写清楚免得被误期待）

| 不做 | 原因 | 何时做 |
|---|---|---|
| **TCP 重组**（跨包匹配） | 先要最小闭环；重组是独立的大工程 | 大任务 9 之后 |
| `threshold` / `detection_filter` / `flowbits` | IR 里表达不了 | P1 |
| **IP 变量表**（`$HOME_NET` 等） | IR 只保留了变量名 | P1 |
| 告警去重 / 抑制 / 聚合 | 属于冷路径 | 接事件总线时 |
| 多模式预筛（Aho-Corasick） | 规则量小时是过度设计 | P1（规则上千条时再上） |
| 引擎修改包/流 | 会破坏"只读输入"的约定 | 永不做 |

> ★ **P0 的能力边界要如实对外说**：因为不做重组，**只能命中"完整落在单个包里"的攻击特征**
> （单包 SQLi、DNS 查询、扫描器指纹这类）。**跨包特征现在看不见。**

## 12. 测试策略

1. **缓冲提取器单测**：逐条断言"取出的字节 == 原文"，以及各种 `nil`（不存在）情形；
2. **匹配语义单测**：条件按序、`offset`/`depth` 相对上次匹配、`nocase`、`negate`、
   **缓冲不存在 × 取反**（§5.4 那张表逐格验证）；
3. **端到端**：一个真实 pcapng 样本 + 一份规则集 → 逐包 解码 → 归流 → 检测 → 断言命中情况；
4. 这套测试同时是**将来上 TCP 重组的回归网**（与规则翻译器用 golden 验收搬家同一套路）。

**现状（已实现，2026-10-11）**：

| 层 | 文件 | 覆盖 |
|---|---|---|
| 字段级单测 | `detect/engine_test.go`（24 条） | 匹配语义、协议 / 端口 / flow 筛选、去重 |
| 规则集测试 | `detect/ruleset_test.go`（4 条） | 计数、报错行号、不支持项、报告输出稳定性 |
| 整链路 e2e | `detect/e2e_test.go` | pcapng → 解码 → 归流 → 检测（已用变异检查证明它会红） |

★ **待补：引擎级 golden 快照（记录每条告警的每个字段）—— 推迟到"上 TCP 重组"时做。**
