# 插件与模块

本文说明平台「外层模块如何以插件形式挂到内核」：进程模型、契约、服务装配、事件约定和当前模块清单。

## 1. 进程模型

```
┌─────────────── 宿主进程（cmd/server）────────────────┐
│  L0 内核（进程内，非插件）                              │
│   bootstrap · registry · pluginhost(Bridge+Manager)   │
│   transport(网关) · eventbus · storage · …             │
│                                                       │
│  宿主桥（net/rpc）：Config / Log / Publish / Poll      │
│   RegisterService / LookupService / RegisterHTTP      │
│   Capture*/Packet*（存储索引）                         │
└───────▲──────────────────────────────▲───────────────┘
        │ go-plugin(net/rpc)          │ HTTP 反代
   ┌────┴────────┐                ┌────┴────────┐
   │ 模块进程 query │                │ 浏览器/前端  │
   │ (L1/L2 插件)  │                │            │
   └─────────────┘                └────────────┘
```

关键约定：

| 约定 | 说明 |
|---|---|
| 内核最小化 | 内核不 import 任何业务模块，只读注册表 |
| 模块 = 独立进程 | 每个模块是 `cmd/plugins/<name>` 编译出的二进制，崩溃不拖垮宿主 |
| 模块间不直连 | 只通过事件总线（Publish/Poll）和服务注入通信 |
| 模块不直连数据库 | 存储经宿主桥，原始 pcap 文件由模块进程自己读写 |
| 可替换 | 换实现 = 换二进制 + 改 json 的 `binary` |
| 可逆副作用 | 模块 Stop 时服务注册 / HTTP 路由自动回滚 |

## 2. 目录结构

```text
pkg/plugin/                插件 SDK（宿主与模块进程共享的契约）
internal/kernel/           L0 内核（宿主进程内）
internal/modules/<name>/   模块业务代码
cmd/plugins/<name>/        每个模块一个进程入口（约 5 行）
registry/backend-modules/  模块身份证（声明式注册表 json）
scripts/build-plugins.sh   一键构建全部模块二进制到 bin/plugins/
```

## 3. 契约（`pkg/plugin`）

### 3.1 Manifest —— 模块身份证

```go
type Manifest struct {
    ID       string   // 模块 ID，如 "modules.query"
    Name     string
    Version  string
    Layer    Layer    // L1 基础 / L2 功能 / L3 扩展
    Depends  []string // 显式依赖的模块 ID
    Provides []string // 提供的服务名（对应 DSH 的 provide）
    Injects  []string // 需要的服务名（对应 DSH 的 inject）
    HTTPBase string   // HTTP 路由前缀；空 = 不提供 HTTP
}
```

### 3.2 Runtime —— 模块进程脚手架

模块只填 4 个字段，其余生命周期由框架处理：

| 字段 | 作用 |
|---|---|
| `Spec Manifest` | 身份声明 |
| `MakeHandler func(host Host) (http.Handler, error)` | 有 HTTP 时构造 handler（宿主桥就绪后调用） |
| `OnStart func(host Host, cfg ConfigSnapshot) error` | 业务启动钩子（后台循环起 goroutine 后立即返回） |
| `OnStop func() error` | 业务停止钩子 |

### 3.3 Host —— 宿主对模块暴露的服务

| 方法 | 用途 |
|---|---|
| `Config()` | 读配置快照 |
| `Log(level, msg)` | 写宿主统一日志 |
| `Publish(topic, data)` / `Poll(topic, since, max)` | 事件总线的发 / 拉 |
| `RegisterHTTP(httpBase, addr, moduleID)` | 上报 HTTP 监听地址（Runtime 自动调用） |
| `RegisterService(ref)` / `LookupService(name)` / `UnregisterService(name)` | 服务注册 / 注入 / 注销 |
| `Capture*` / `Packet*` | 抓包与数据包的元数据索引（模块不直连数据库） |

## 4. 服务装配（provides / injects）

1. 宿主先由所有模块的 `Provides` 建「服务名 → 提供者模块」映射；
2. 每个模块的 `Injects` 展开成对提供者模块的隐含依赖，与 `Depends` 一起参与拓扑排序；
3. 因此只要 `Injects` 写得对，就不用写 `Depends`：框架保证提供者先启动、消费者后启动；
4. 注入的服务名找不到提供者 → 启动直接报错（不静默降级）；循环依赖 → 报错并列出卡住的模块。

`ServiceRef.Kind`：

- `http`：模块有自己的 HTTP 服务，Endpoint 是监听地址；
- `bus`：纯后台模块，Endpoint 是其模块 ID（数据走事件总线主题）。

## 5. 事件主题约定

| 主题 | 生产者 | 消费者 |
|---|---|---|
| `detect.feature` | 行为检测 / 规则命中 | situation、attackchain |
| `situation.level` | situation | disposal、alert、前端 WS |
| `alert.lifecycle` | alert | 前端、导出 |
| `disposal.audit` | disposal | 审计、前端 |

事件 `data` 为 JSON；共享事件类型定义在 `internal/kernel/datamodel/threat.go`。
